# 账号复盘与人机共创设计

本文记录 2026-10-03 关于内容生成和四个外部 Skill 的讨论，是下一阶段的设计稿，**不是已完成功能清单**。当前实现以 PRD 和状态记录为准。

**最新实现（核对至 2026-10-11）**：公开创作使用单创作 Agent，左侧对话、右侧稿件；用户可添加原笔记、账号分析／受众分析的具体历史作为参考，默认不读全账号。原笔记通过统一选择器逐篇添加，助手只读取所选篇目的完整已保存标题／正文，不带入评论、指标或图片。材料集或所选原文变化划分新的上下文段，旧对话仍可看但不自动污染新输入。复用现有 session/message、Qwen、异步恢复、选段精修和人工采用，不简单回滚旧单助手或重写通用框架。详细契约和验收见[本轮改造计划](creator-workspace-refinement-plan.md#五单创作助手与用户控制的参考材料)。导航把选题库和创作助手放在受众流程之后，仍可直接进入。

历史：2026-10-06 曾决定采用由 LangGraph 驱动的消息式协作父图，研究、写作、评审为可见角色，并已接入公开画布。下文保留其实施记录以维护旧历史与既有执行能力；这不再是公开创作新请求的目标模式。账号诊断和受众 Panel 的执行方式不因本次单助手改造而撤销。协议、上下文和持久化边界见[Agent Runtime and Context Architecture](agent-runtime-architecture.md)。

## 当前实施进度

### 当前补充：原笔记参考已接入，写作质量继续验证

原笔记与分析历史合计最多 8 份，一篇笔记算一份，48,000 序列化字符上限不静默截断。可按时间、点赞或已记录互动选择，确认前预览、确认后逐篇移除；未发送参考及输入在当前标签页按账号／选题暂存。所选原文更新会开启新对话段，仅指标或评论更新不会；发送时冻结原文，不回写旧历史。特定读者意见仍从已有 `writingFocus` 入口带入，不自动读取整场群聊。

引用范围、上下文隔离和交互已通过回归；原笔记参考尚未完成真实模型的口吻与事实保持对照，不能据此宣称写作质量已提升。账号复盘已采用整体认识、代表作精读、汇总的增强默认流程，但仍有语义误读，详细记录见[当前状态](status-and-todo.md)。下方保留各轮当时的进度，其中“原笔记待接入”等首批限制已被本段更新取代。

### 2026-10-10 首批：一个助手、作者自选分析参考、左聊右稿

新会话显式使用 `single_writer`，一条请求仅有一个写作回合，完成后直接交给作者。参考选择只接入同账号、已完成的账号／受众分析结果；支持多选、摘要预览、移除和缺失记录恢复，8 份／48,000 序列化字符上限不静默截断。空选择不读取全库，选中结果也不递归带入原始材料；服务端冻结内容、范围、来源版本、生成来源与稿件版本。参考增删后的新请求只接收新段最近 12 条消息，不把旧摘要当隐形上下文。

桌面左聊右稿，窄屏双页签保留输入和滚动；选段动作定位对话、建议预览定位稿件，Esc 关闭参考弹窗后回到原按钮。保留人工采用与保存，生成期间编辑不会被迟到结果覆盖。运行中修改参考只对下条消息生效；重开恢复上次已发送参考，未发送调整暂不持久化。旧两种对话按原身份只读展示。

单次生成完成后展示简短回复和候选，等待期间只有真实状态与耗时；尚无单次模型调用中的可交付分段。已导入笔记选择作为独立参考类型仍待接入，读者特定意见沿用原 `writingFocus` 入口。界面和上下文回归通过，但构造稿 Qwen 检查仍有措辞不自然和轻微改义：已修复字符串引用导致的格式失败，没有把格式通过视为写作质量通过，也未重写旧作品或历史。

### 2026-10-09：创作试读修改卡的阅读层整理

问题：EditorFeedbackView 同时展开理由、读者顾虑、受益者和取舍，具体建议及预览入口被解释推后；只读历史还统一声称“尚未写入”，与已采用提案可能矛盾。

本轮范围为组件及专用 CSS，不改模型、提案或保存服务。卡片默认呈现修改类型、核对过的标题／正文位置、观察和具体表达／待补素材；预览入口先于依据。保留项和没有具体替换稿的建议直接展示理由；其他理由、取舍、读者记录和完整冻结原文按需展开。同一问题的多个方案仍成组，共同顾虑只留一份。移除面向内部的核验数量，不隐藏实际保存失败或过期提示；空结果保留简短可行动说明，旧总结继续由原入口展示。历史只读不推断是否采用。

验收：正文 14px、区块 16px、辅助 12–13px，白底灰线、动作沿用统一按钮；长中文／URL 与 320–390px 窄屏不溢出。定向及完整前端测试覆盖展开、冻结原文、非公开顾虑标记、旧记录、预览前不写入、确认采用／撤销及版本过期。隔离浏览器用已存真实修改卡与标注的边界样例核对动作和布局，不调用模型、不写正式库。涉及 EditorFeedbackView、App.css 中该组件规则、对应测试及交接文档。

### 2026-10-08：文字层级与信息密度收敛

用户要求字体、字号、字色、文字量克制。本轮不改字段与业务流程：沿用系统无衬线字体，正文 14px、辅助文字 12–13px、区块标题 16px、页面标题 24px；强调优先 600 字重。正文与说明只用深灰／次灰，蓝色用于动作，失败／状态保留必要语义色，不用低对比灰掩盖信息。先收紧创作画布、协作聊天和模拟群聊，其他旧页逐步使用共用字号变量，不宣称全站每条旧样式已迁移。

界面删除重复的角色分工、等待过程与改稿教程；同一动作的保存提示只留一处，引用保留原文，长说明按需展开，不截断作品或模型结果。预览统一白底、灰边，不叠蓝／绿／棕色说明卡；昵称不大于正文，回复对象低一级。预期修改 App.css、LocalRewrite.css、ContentCollaborationChat.css、TrialRoom.css 和对应组件。验收：组件回归、构建／lint；隔离浏览器检查桌面与 390px 的计算字号、颜色、预览／输入操作与溢出，保留必要错误与未保存提示。

### 2026-10-08：读者意见 → 局部改写 → 同组复测（交互已实现，内容质量仍在改进）

按用户确认的顺序，先连接群聊意见与创作，再实现选段精修，最后用四账号检查实际写作结果。复用现有协作 session/message、人工保存和同组复测，不新增另一套 agent 执行器。

- **意见入口**：创作级模拟的公开留言、互相回应和作者访谈回复可选择“拿这条意见改稿”。跳转对应选题并显示所选原话和来源；不自动发送、不自动改稿。账号级与已发布笔记级仍使用已有后续选题入口，不覆盖历史笔记。沉默、内部试读记录不伪装成公开意见。
- **选段操作**：正文选中一段后可选择“更像我的口吻／更简洁／讲清楚”，要求先填入对话，作者可改后发送。选段和引用意见可组合，也可单独使用；意见不是作者确认的新事实。暂不新增多段批处理。
- **上下文字段**：协作消息新增可选 `writingFocus`，含 `expectedUpdatedAt`、`selection{start,end,text}`（Unicode code point 下标）和 `readerReference{simulationId,stage,messageId,interviewId?}`。后台从保存记录核对公开原话、同账号同稿件及选段，冻结 `baseTopicId/baseTitle/baseBody/baseUpdatedAt` 与来源；每个角色继承同一任务范围，历史请求与无选段请求保持兼容。
- **结果与采用**：局部表述候选只返回替换片段；预览展示选中原文与建议，可编辑。程序只替换所选位置，重复句子、emoji 和换行不靠字符串搜索猜定位。画布已变化则保留新稿并要求重新选择；放入画布不等于已保存。完成保存后，可沿用原次模拟的人物和任务复测。
- **验收**：组件测试覆盖没有自动请求、引用选择／移除、跨账号隔离、重复片段与 Unicode 定位、等待期间继续编辑、旧候选兼容；服务测试覆盖来源验证、版本冲突、重放与每角色任务包。浏览器检查桌面／窄屏、键盘和前后预览。四账号各一篇、每篇两位固定读者独立反应，写作角色判断是否修改；有合法替换稿时再由所选意见的同一读者复看，最多每档 4 次、总 16 次 HTTP，无自动重试、不生成新人物、不写正式资产。实际共 13 次，结果见[四账号回归](four-account-regression.md)。分别记录作者声音、关切变化、事实新增与人物判断，不能把 JSON 或测试通过当成质量通过。

实现文件覆盖群聊／历史／App 导航、创作画布／协作聊天及类型，协作模型／持久化／provider、新 writing focus 服务与测试，以及独立四账号验收脚本。局部建议在预览时定位到可见区域，选段动作把焦点送到消息输入框；新回复不主动抢焦点。旧定位不完整的候选仍可读，但不允许猜位置替换。具体完成和失败记录以状态文档为准。

真实检查后补充写作决策：读者认可原句时允许说明保留，不为改而改；必要改写保留核心动作、责任主体和判断强度。缺少关键素材可以追问，但优先只问一个具体观察或依据，不逼作者解释未知机制，不列资料清单。素材足够的精简／语序／口吻调整直接给可用文字。模拟读者的新问题不得说成自己此前已提出的困惑，复看允许更喜欢原稿。上述提示调整并不等于四账号写作效果全部验收。

### 2026-10-08：公开创作画布接入协作主路径

旧单助手不再接收公开画布的新消息。右侧改为研究／写作／审稿协作室，使用持久化 session/message 接口，每位角色完成后就显示阶段结果、中文回复对象和可预览候选；耗时和恢复读取可见，旧对话保留为只读折叠内容。候选可编辑后放入标题或正文，再由作者保存；未采用候选和用户未保存输入不会被迟到结果覆盖。每条新创作者指令冻结发送时最新已保存 Topic，幂等重发继续用原冻结输入。

目前是按角色完成后的分段展示，不是逐 token 流式输出，也不暴露隐藏推理。读者试读采用独立群聊视图，并可点名追问；作者访谈与原始模拟分开持久化，不能把新访谈改写成当初的独立反应。

### 2026-10-06：画布改稿进入显式提案边界

从此日期起，经过本次事实核验的 AI 画布改稿也**不会自动写入 Topic**。后台先冻结 `creator-edit/v1` 快照：本次执行看到的 `before`（标题、正文、版本）、通过校验的 `suggested`，以及尚为空的 `after`；消息标记为 `pending_confirmation`。随后生成 `topic.apply_canvas_edit` 提案，创作者需要显式采用，才会写入当前稿件。

采用前可以按当前稿件预览；采用时再次核对冻结的 `expectedUpdatedAt`。在建议生成后有任何手动保存或其他更新，提案会冲突而不是覆盖新稿。重复采用只返回同一份回执，不重复写入。这个保护复用资产提案和 Panel 改稿共同使用的提案生命周期，而不是让模型或画布前端自己决定何时可覆盖。

`topic.apply_canvas_edit` 是服务器在画布事实核验后派生的保留动作：普通 agent 返回的同名动作会被丢弃，通用提案编辑接口不能重写它的标题、正文、版本或目标 Topic。创建时会把目标绑定到当前画布对话的 Topic，避免“看起来像一条建议”的外部输出绕过冻结快照。

这项改动不重写旧历史：过去自动写入的对话继续显示其当时保存的 `after` 和“当时已应用”含义；冲突和旧字段缺失的记录也仍可读。多角色协作现已具备持久化会话、追加消息、运行回执和默认走 Qwen 的 specialist 单回合；本地确定性 demo 仍可显式选择，用于无密钥演示和测试。真实角色只能读取创建 session 时冻结的 Topic／工作区投影，输出只能形成只读讨论候选，不能直接修改 Topic 或 Draft。它仍没有候选素材表、SSE 事件或画布内协作展示，因此还不是面向创作者的完整协作界面。

### 2026-10-06：角色任务包与结构化交接

此前 research、writing、review 基本共享同一份大上下文，只在提示词末尾用角色名区分；上游的 `candidateSuggestions` 虽写入消息元数据，却没有送到下一角色。这会让三个角色更像同一位助手的换语气复述，而不是协作。

现在每回合会基于已冻结的材料组装 `content-collaboration-role-packet/v2`：research 优先看到当前选题、账号定位和历史证据概览；writing 优先看到研究候选及其原始引用；review 优先看到具体写作候选及其依赖的证据。候选在消息落库后获得稳定的 `candidateId`，下一角色必须通过 `usedCandidateIds` 明确说明自己承接了哪一条。研究转写作前要给可用证据；写作转评审前要给可评审的结构或表述；评审要明确指向上游结构。这样保留角色间可追溯的工作关系，而不是让完整聊天记录反复污染每轮输入。

质量不是靠把所有建议都压成保守措辞：证据判断和创作建议现在明确分开。模型可以提出大胆的新写法，但只要补入输入没有的时间、经历、因果或例句，就必须标成推断／待创作者确认，不能借一条相关引文说成已知事实。

2026-10-04 用户确认受众 Panel 四阶段，详见[实施计划](audience-panel-four-stage-plan.md)。当时确认的模拟反馈链路采用“查看意见 → 选择要处理的反馈 → 待确认改稿提案 → 显式采用”，不要直接调用当时会自动写稿的普通创作对话作为替代。2026-10-06 已将同样的确认边界扩展到画布 AI 改稿；Panel 的反馈来源、段落定位、持久提案和同组复测继续按各自计划演进。

最新画像验证见[状态记录](status-and-todo.md)：较早新提示已有一次 84.35 秒成功结果，仍发现跨经历归纳与低互动解释问题；随后新增规则的请求在完成发送后等待响应头 90 秒超时，未形成可审阅输出。下面保留此前各轮过程，不把“暂无输出”的历史说明当作当前全部检查均失败，也不将单次返回视为语义已验收。

最新延长读取对照在 98.69 秒成功，因此 Qwen 画像现单独默认读取等待 180 秒。低互动原因留空，但跨经历、引文和无依据互动率仍有问题；本轮只确认执行等待改善，不将生成建议直接变成可采用经验或账号偏好。后续先推进创作前后快照的可靠记录，避免只围绕同一提示反复付费验证。

结果页已接入四指标切换：显示有效数量、中位数、缺失数与按当前指标排列的笔记。每组最多两条，同值不会被分到高低两侧；缺少点赞也可查看收藏、评论或分享。旧历史按冻结的逐条指标补算只读展示，不回写历史或取当前素材。该界面补齐表现浏览，不代表模型经验卡或创作采用流程已经完成。

创作助手的四种合作模式现已写入 CREATOR_EDIT prompt：讨论只给不同方向；明确起草可直接写；定向修改要求未指定部分逐字保留并返回完整稿件；只做风格检查时先给建议不自动修改。原 schema、后台执行及合法修改自动应用机制未变，这不是提案确认功能上线。新增 `scripts/check_creator_edit.py` 用构造样本分别检查讨论、风格建议、只改标题、只改开头和初稿；默认免费预览，显式 live 每次仅调用一次 Qwen、不写业务库。已用真实 qwen-plus 验证“只改开头”和“只讨论”：前者保留标题与后续段落及换行，后者 update=null 且两个方向有实质差别。讨论回复略长；其余模式尚未真实验收，服务端也尚未独立识别并强制执行自然语言修改范围。

随后已将方法增量写入 PROFILE 提示词：先认识账号、分指标比较具体笔记、观察观点／论据／开头／推进／语气，并在既有 contrast.takeaways 字符串中表达“参考写法 → 适用场景 → 具体调整”。新增方法不改变输出结构，不建立独立经验卡，创作助手提示词尚未在这轮修改。真实对照检查的旧提示请求 90 秒超时，无模型正文；因此取消新提示的第二次调用，新规则仅完成工程回归，内容效果尚未验证。

在上方创作助手短请求成功后，另补一次完整画像新提示检查，仍约 91 秒 ReadTimeout，无正文；不重试、不据此归因于提示词，复盘效果对照仍未完成。当前已完成的是两项创作模式的样例验证，不是全链路效果验收。

2026-10-03 已实现切片 1 的计算底座：新诊断的 `stageResults.profile.observations` 新增 `metricSummaries`（四指标各自的有效数、缺失数、中位数与排名方式），每条笔记新增 `metricRanksInSelection`。并列采用稠密降序名次，原 `likesRankInSelection` 保留兼容；不补写旧分析。该增量沿用现有 observations/v1 的可选字段扩展，没有新增下文拟议的 contentReview 结构。页面进展见上方，模型输入仍未加入这些汇总，经验卡、确认与撤销尚未实现。

## 要解决什么

账号诊断先帮助创作者理解自己的特点和优势，复盘再回答哪些写法值得继续尝试；创作助手负责把这些认识变成一篇用户愿意发布的稿件。用户决定想说什么、个人经历是否真实，以及最终采用哪一种表达；AI 提供角度、组织材料、起草和修改。用户可以直接让 AI 起草，也可以只讨论，不必依次完成需求表、提纲、初稿的固定流程。

目前公开创作助手已经是左侧标题／正文、右侧对话的画布，实际编辑 Topic，不是内部独立 Draft。对话和已保存正文可以重开；2026-10-06 起，AI 返回通过校验的完整修改会先成为待确认的 `topic.apply_canvas_edit`，而非直接更新 Topic。遇到版本冲突保留建议而不覆盖新稿；旧自动应用历史仍以当时回执展示。已有消息内有只读前后对照，选区改稿、有限撤销和可确认的账号写作偏好仍待后续切片。现有事实检查验证模型声明的引用和待确认内容，不能自动发现所有未经声明的新增事实。

账号诊断已经保存逐条互动数、日期、范围和画像依据；页面已支持四项互动指标独立切换，模型归纳仍沿用原字段。下面拟议的 contentReview、独立创作经验卡及修改提案尚未实现，不把已有统计和文字建议等同于这些产品能力。

## 复盘产出：让优势变成可用经验

程序负责从本次 AnalysisRun 冻结输入计算每篇的赞、收藏、评论、分享及缺失情况，分别提供样本内排名和中位数。缺失不是零，各指标使用自己的有效样本数；不将四种互动相加成一个内容质量分。模型负责结合正文解释差异，例如某篇收藏相对突出，可能是内容更便于日后使用，但必须同时看具体内容，不能仅靠一个数字认定读者动机。

结果页保持“账号关键词与优势 → 具体笔记比较 → 可尝试的写作经验”的顺序。默认给出少量最有帮助的对照，不先铺满指标表。每条比较能打开当次笔记，展开后查看数值与分析范围。发布时间不同的累计数据可以并列，但不能直接得出增长率或因果结论；四篇甚至更少也能复盘，不硬凑共性，更不因为样本少就拒绝帮助。

拟在现有 profile 阶段结果中增加可选的 `contentReview`，旧历史缺字段就维持旧展示：

| 字段 | 内容与责任 |
| --- | --- |
| `schemaVersion`、`scope` | 程序保存规则版本、分析运行、选中笔记 ID、采集时间；不复制完整正文 |
| `metricSummaries[]` | 程序计算指标名、有效／缺失数量、中位数及逐条排名；并列值采用相同名次 |
| `comparisons[]` | 引用笔记 ID、比较维度、具体观察、解释与适用限制；原始数值由程序关联，不由模型重新填写 |
| `experiences[]` | 本次运行内稳定 ID、短标题、可复用写法、适用场景、不适用场景、支持笔记、反例及下次可尝试的变化 |

例如“把抽象选择写成具体取舍过程”，比“多写高价值内容”更值得保存。支持笔记和反例允许用户自行判断，不要求每条经验都伪装成确定的成功规律。界面文案可以积极直接：告诉用户已有的长处和下一次如何发挥，把数据说明收进详情，而不是反复提醒不确定性。

生成经验属于不可变的分析结果。用户选择“本篇采用／记为账号偏好／暂不采用”属于另一份可编辑记录，不能写回 AnalysisRun。首版不强求独立经验库：本篇选择保存在 Topic 的创作设置中，账号长期偏好保存在账号范围的设置中，均引用原运行和经验 ID，并保留用户确认的文字。名称是拟定字段，不是现有 API。

## 共创方式与界面

进入创作助手先显示当前选题和正文。空正文只提供一个主要动作“帮我起草”，次要入口“先聊角度”；用户也可直接输入要求。有正文时继续编辑和对话，不重复询问已经明确的背景。确实影响写作的材料缺口才问一个具体问题，不能每次都让用户重填账号信息。

探索角度时给两到三个真正不同的方案，例如经验复盘、选择方法、观点讨论，而不是同一句话的标题改写。每个方案只显示一句核心表达和简短理由。历史经验和风格来源放在“本篇参考”中按需展开，用户可取消，不占据主编辑区。

定向修改可来自对话，也可来自选中文本后的“改写”。用户可以明确只改标题、开头或某一段；AI 不应借机改掉全文的观点和个人经历。风格检查以用户确认的偏好和代表作作参照，提出少量“这里可以更像你”的建议，不自动重写。用户说“这篇想换一种风格”可以覆盖本篇规则，但不自动改掉账号偏好。

**当前交互默认值**：无论空稿还是已有正文，模型返回的画布改动均先展示为可回看的建议，并要求创作者采用；讨论永远不修改正文。不能靠模型判断“改得算不算大”绕过确认。局部修改应只展示目标段落的前后对照，全文修改再展开全文，避免每次生成一个庞大弹窗。当前后端已经强制“先提案、后写入”；画布对待确认提案的最终可见性与交互检验仍随前端切片单独记录。

受众模拟仍是用户触发的下一步。点击“选择模拟读者”先保存当前稿件、进入既有确认页，不自动付费模拟。模拟结果回来后，用户选择想处理的疑问再交给创作助手；这些内容标为模拟反馈，不当作真实评论，也不让每个不同意见都变成必须满足的改稿任务。

## 数据、执行与编辑边界

无需版本表，但修改必须可追溯。当前画布建议已保存为现有对话消息中的不可变 `canvasEditSnapshot`，并通过资产提案记录 `topic.apply_canvas_edit`：提案 ID、所属账号和 Topic、动作类型、基础 `expectedUpdatedAt`、修改前标题／正文、建议结果及模型元数据。局部改稿后续再补范围及原文锚点；重复句子不能靠第一次字符串匹配定位。用户的采用、拒绝及以后可能的撤销状态由后端维护，模型不能自行写“已采用”。

当前采用接口复用受控的资产提案执行器，而不是让对话任务直接写 Topic。它在一个事务内核验账号归属、基础版本和提案状态，再更新 Topic、记录应用回执。重复采用返回原回执，不再次写入；版本过期展示冲突，让用户基于新稿重做建议，不能覆盖。Panel 的受限撤销已有独立生命周期；画布建议的撤销语义尚未接入，不能把旧自动应用历史或未来画布提案误当作可安全回滚。

原始生成快照仍保持原样，用户修改只改变 Topic 当前标题／正文。刷新后可重新打开提案和应用状态，不靠浏览器记住是否采用。模型执行继续使用已有独立后台任务，观察不触发新请求；中断保留原稿及失败信息，不以空稿替代，不自动重发未知计费请求。提案在服务端生成时就冻结基础版本，不能在应用时临时读取最新版冒充原基础。

创作上下文保留账号全局视野，但区分用途：账号概要与关键词、当前稿件、用户本次要求、本篇选择的经验、已确认风格、必要的近期对话，以及可追溯的原始材料。助手可以进一步取得同账号材料，不必让每次改标题都携带所有历史运行、能力目录和模拟讨论。用户本次提供的经历和要求优先于旧推测；模型自己写出的初稿不能循环成为新事实来源。

接受一段文字只表示用户喜欢这次表达，不表示它会有高互动。只有明确选择“记为账号偏好”才更新长期风格；只有之后导入的实际发布结果才可能成为表现复盘素材。首版不实现自动识别发布笔记或学习闭环，避免把模拟结果、用户采用率和真实传播表现混在一起。

# 路线图

更新日期：2026-11-07。现状见[项目总览](project-overview.md)。本文只列待做的事和顺序；做完后把结果记进[状态记录](status-and-todo.md)，并从这里删除或更新对应条目。

排序原则来自用户的长期要求：先处理交付失败、事实可靠性和实际等待，再做新功能；不把“加功能”或“再加一轮校验调用”当作默认推进方式；真实模型实验要小规模、问题明确、事先说清预算。

## P1 质量与可靠性

1. **验收账号诊断的图片文字与局部恢复**
   - 做法：在临时库中选1～2篇正文主要写在图片里的笔记，核对原图 → 识别文字 → 报告引用；再人为制造一个阶段失败，确认成功部分不重复调用、失败部分可以恢复。
   - 验收：保存模型原文、调用次数和等待时间，由用户判断识别质量。
   - 前提：用户确认样本和调用预算，模型沿用DeepSeek。
2. **创作的事实可靠性**
   - 做法：先列出资料包里任务、事实来源、说话人和原稿版本是怎样区分的，再用已知出错的稿件和确有亲历的正例回放。
   - 验收：对照完整成稿、等待时间和人工采用情况，不以禁词是否消失为准。
   - 参考：[事实来源回归](creator-source-attribution-regression-20261017.md)、[推断事实化回归](creator-inference-facts-regression-20261017.md)、[改稿去重回归](creator-revision-dedup-20261017.md)。

- **读者模拟与真实评论的差距**（来自[读者模拟回测](reader-simulation-backtest-20261108.md)，2026-11-08）：在 5 篇留出笔记上，模拟读者组几乎没有复现真实评论，直接预测评论更接近；演示时不宜称为“预测评论区”。先由用户抽查标注，再决定是否调整读者提示（减少找缺口的倾向、限制同问式回应）或让模拟读到图片文字。任何调整都要用同一脚本重新回测。

## P2 等待时间与工程债

3. **受众模拟的长尾等待**（来自[等待与失败统计](wait-and-failure-stats-20261107.md)，2026-11-07 已完成统计）：
   - DeepSeek 下初读、回应约 3 秒，但 10-17 实测中失败的请求要等 31.8 秒和 75.0 秒，汇总偶发 78.6 秒，整场讨论被拉长到 38 秒，定点恢复另用 157.6 秒。这次实测早于当天下午加入 30 秒每环节上限、去掉隐式重试的`a8220c5`，现行代码还没有真实复测。
   - 根因已查明：传输失败被`_call_deepseek`改写成校验错误，界面显示英文原文；78.6 秒的汇总规模正常，慢在服务或网络一侧，在现行 30 秒上限下会被截断。
   - 2026-11-07 已修复（未提交）：传输失败单独归类并保留异常类型；页面用中文分别说明没有收到回复、等待超时、格式不符合要求和服务返回错误；读者环节保持30秒，汇总改为90秒；每个环节的耗时和失败类型写进`stepRecords`。自动测试通过，没有真实复测。
   - 剩余：用真实调用复测一次（QSheep、一粒鱼各一场，约12～16次DeepSeek请求），需用户确认预算；正在运行的开发实例需要重启才会用上新代码。
4. **在产品记录里补上计时与失败类型**：在现有模型元数据中写入每次调用的耗时、尝试次数和失败类型，并区分“没有收到回复”和“格式不通过”。不增加调用。受众模拟已在2026-11-07补上（`stepRecords`），账号诊断和创作还没有。现在 DeepSeek 时期的产品运行只有 2 次诊断，统计主要靠实验脚本；补上后可以直接用真实运行复查。
5. **把`assistant_mode`的默认值改为`single_writer`**：`models.py:428,599`和`content_collaboration_sessions.py`。先查清哪些旧调用方依赖`legacy_team`，旧会话保持只读可读。
6. **迁移编号0024重复**：两个文件共用一个编号。先确认迁移执行器按什么排序、已有库里记录的是哪个文件名，再决定是否需要处理。不改已应用迁移的内容。
7. **窄屏引导遮挡**：375宽下“我的笔记”引导第2步的目标卡片约420px高，说明卡只能叠在卡片底部。可以让高目标滚动到视口上方，或只高亮卡片的上半部分。

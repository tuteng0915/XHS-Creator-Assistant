# 创作事实归属：读者处境为什么变成作者亲历

## 本轮结论

输入确有两类归属混淆，但不是程序把一句已有事实直接复制错了：

1. **任务重复充当证据。** 一粒鱼请求里的“开头回应觉得自己没做过大项目的应届生”在实际messages里出现3次：creativeBrief、allowedSources、最后的真实user消息。整条创作要求还归在authorMessages中。模型没有收到“很多应届生跟我说”这句话，却自己把受众处境补成了作者曾被咨询的场景。
2. **出版／选择原文与原文叙述者混为一人。** 一粒鱼原文以“这篇来自🍻”开头，招聘段落中的“我”属于原文叙述者；诊断却以“你用……实例解释ownership”提供编辑观察。旧输入缺少按文档区分的叙述者范围，roleTask还要求“保留其具体经历”，写作身份容易顺势接过招聘人的“我”。

这些是可核对的上下文设计问题；不能据此证明模型内部的唯一因果路径。社交写作惯用的“很多人问我”开场也可能参与了生成，当前没有单独隔离其影响。

本轮不是再加禁令：**系统提示全文保持1788字符不变**，模型、非思考、temperature=0.3、1800 token预算不变。修改的是模型输入组织，没有追加审稿模型、事实检查调用、重试或正文词语替换。

## 实现

- `creator-writing-packet/v2`：当前要求只通过真实user消息传一次，不再复制进creativeBrief；用户历史仍是user，模型历史仍是assistant。
- 证据目录中保留作者对话的sourceId及dialogueIndex，不复制其全文。真实补充仍在实际对话中，后台保留原文字典供逐字引用验证，所以不是把作者补充事实删掉。
- 稿件、原笔记、编辑分析、历史评论、读者意见、作者对话用不同sourceRole表示；取消roleTask中重复的事实禁令和默认要求保留作者亲历的措辞。所选原文、报告观察与评论引文没有被删减或改写。
- 原文叙述者的speakerScope按sourceId分开；选择原文不自动建立其叙述者与当前作者的身份绑定。作者明确补充仍可确认自己的经历，不需要人工确认新流程或额外必填字段。这个标记不是自动识别出了真实身份，也不是语义保证。
- 首稿数据帧由QSheep12386→11902字符、一粒鱼9471→8724字符（第一阶段）。最终叙述者范围补充只增加文档身份元数据，任务仍只出现一次；没有扩大全账号读取范围或把更多历史送入。
- 检查发现另一处无意义硬限制：QSheep生成5条有效引用却被最多3条拒收。取消共用候选的引用条数硬上限，仍逐条校验来源、逐字引文、单条长度；不截成3条丢证据。旧团队也受益于这一引用数量放宽，角色路由和其他权限不变。

## 关键原文对照

### 一粒鱼首稿：读者处境变为作者接触

修改前：

> 很多应届生跟我说：我只有一段普通实习，没做过什么大项目，怎么讲闭环？

第一阶段后：

> 很多人觉得自己简历上没东西可写，是因为没做过大项目。但筛简历的人真正在意的，往往不是你参与过什么级别的项目，而是你有没有把一件事从发现问题推到有人用上。

后者不再编作者接触经历，但“筛简历的人真正在意的”仍是泛化判断，并不是事实遵从完全通过。

### 一粒鱼明确事实：保留案例，不接管叙述者

第一阶段仍出错：

> 我后来给出去的一个商家运营岗sp offer，候选人是一个非常普通211的学生……

第二阶段：

> 聊ownership，很多人第一反应是扛大项目、拿大结果。但原笔记里那个拿到商家运营岗sp offer的候选人，恰恰是靠一件小事被看见的。她是一个非常普通的211学生，只有一段不够匹配的中小型电商活动运营实习，简历上并不占优。她出彩的地方在于：发现平台一个大促链接的手动配置容易出错，就自己利用闲暇时间做了一个配置模板，主动和产研去对，最后真的降低了配置错误率。这件事不大，甚至不在她的岗位职责里。但ownership往往就藏在这种地方——不是等别人派活，而是看见一个反复出错的环节，判断它值得被解决，然后真的动手把它解决掉，还推着相关的人一起把它落地。

这里案例主体保住了，但“甚至不在她的岗位职责里”原文未明确，仍应改进，不能因有两条有效引用就整体认定属实。

### QSheep：不要因谨慎删掉真实作者事实

第二阶段摘录：

> ……最支持我出国的是我爸爸，他的MBA毕业于MIT，他认可换一个海外环境读书可以带来的益处。……目标这一项，我明确知道自己毕业后的第一步是就业。

两项均保留，未把父亲学位写成作者学历，也未把作者先就业改成保证就业结果。但约250字的任务仍写长，引用也多于旧硬上限。

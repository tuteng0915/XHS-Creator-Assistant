# 创作者工作区 PRD（Reverse PRD）

## 2026-10-09 当前交互决定（优先于下文历史方案）

- 创作级试读修改卡先显示修改类型、已核对的标题／正文／全文位置、具体建议或待补素材，再显示预览入口；理由、取舍、受益读者、来源与完整冻结原文按需展开。保留项以及没有具体替换稿的建议直接显示理由，避免只剩标题。同一问题的多种改法保留独立选择，共同顾虑只展示一份。内部核验计数不展示，但仍筛除无效卡；空结果与保存失败／过期提示保留。只读历史不声称“尚未采用”，采用状态以提案回执为准。全文建议仍不支持局部替换，预览和确认边界不变。
- 受众候选先呈现人物判断方式、具体需求与宽兴趣；收录按钮位于补充详情之前，页面统一展示人数／已收录数，避免每卡重复状态。表达习惯和来源按需展开；引用等于完整评论时只显示一遍，不改原记录。账号／已发布笔记复盘先给摘要与后续建议，需求、保留项及选题理由按需展开；选题标题、角度与手动加入动作常显。无摘要但有有效建议仍展示新版结果，只有旧修改卡的历史也可读取。该呈现切片不改变模型输出。
- API 结果以阅读任务组织，不直接按字段铺满等权卡片。账号画像先显示概要、关键词与原顺序前三项优势，更多优势及方向／价值／表达／近期变化按需展开；完整结论、引用和历史快照保留。笔记表现为对齐列表，样本与时间收在末尾。无旧归纳不留空折叠区；旧格式仍可读，未知阶段在公开页给简短提示，不直接显示 JSON。首轮只改呈现，不缩写模型结论、不改变数据或分析质量判定。
- 受众分析不向作者展示“若干分组未通过核验”、被拒原因和技术校验说明；可用读者正常显示、逐位收录。原始输出与诊断继续留后台，不放宽筛选。旧历史中的固定核验附言只在展示时移除，不改保存记录；没有可用结果时提供简短的重新分析提示。验证覆盖部分结果、旧附言、零结果与收录行为。
- 文字视觉克制：沿用系统字体，主路径正文 14px、说明 12–13px、区块标题 16px、页面标题 24px，常规强调 600 字重；正文／辅助说明使用深灰／次灰，不用多套蓝灰或棕色文字区分模块。蓝色留给动作，必要状态保留语义色。创作画布／协作与受众群聊先统一，旧页逐步迁移。操作说明就近留一句，不反复介绍角色分工；选段原文按需展开，真实作品／发言不截断，错误、耗时及未保存提示保留。
- 创作级群聊的公开意见和作者访谈回复可“拿这条意见改稿”，带回对应创作并显示原话与当时提问；仅建立引用，不自动发送或改稿。选段可与引用组合使用，支持更像原稿口吻、更简洁、讲清观点；点击先填要求，由作者确认发送。旧身份或定位缺失的记录保持可读，不伪造可改稿入口。
- 局部建议展示修改前／后，允许编辑建议后“只替换这一段”；按服务端冻结的选区与原稿定位，不以首个同名句猜位置，不动其他正文。画布已变化就要求重新选择，不覆盖新稿；采用后仍需保存，保存后可邀请原班读者复测。此前讨论和人物保持原快照。
- 写作伙伴可判断“这句值得保留”，不把每条好评都转成修改任务。确实缺素材时先问一个容易回答的场景或依据；材料足够的表达改善应直接交稿，不把未知背景变成处处停顿。人物意见是参考，不自动升级成作者事实；产品功能通过与真实改稿质量分开验收。
- 按钮使用全站公共样式：普通操作 36px 最小高度、14px 字号、8px 圆角；新建／保存／发送／开始等主操作为蓝色，次操作为白底灰蓝边，放弃未保存修改用危险色，依据／展开用文字按钮，关闭用等宽图标按钮。禁用、悬停、按下、键盘焦点共享规则。各页面只管理按钮摆放，不再各自定义一套皮肤；导航、页签、笔记／历史选择卡保留其布局。窄屏操作区与保存状态允许换行。
- **受众模拟是独立一级入口**，不分散成账号／笔记／创作三个页面，也不强制用户先模拟再创作。导航保持“账号概览／我的笔记 → 账号诊断／分析历史 → 选题库／AI 创作助手 → 受众分析／模拟粉丝 → 受众模拟”的自然顺序；来源页可预选目标后带到同一入口。
- 统一页先选“账号级／已发布笔记级／创作级”，每类单独筛选历史。共用“选择对象 → 推荐或手选读者 → 调整本次角色并确认 → 群聊／作者追问”。默认账号级；新建运行或旧记录读取的迟到响应不抢走当前类别和已打开的记录。
- 账号级从已导入文字中均匀抽取最多 12 篇，每篇最多 1200 字，冻结简介、样本与范围说明；推荐和模拟读取同一目标。它回答长期阅读期待和持续方向。已发布笔记级冻结所选原文，结论面向下一篇同类型内容，不编辑已发布原文。创作级才沿用当前稿件的编辑反馈和确认改稿。
- 账号级与已发布笔记级可以产出后续选题候选；作者点击“加入选题库”才创建 Topic。同一个候选重复点击返回原选题，不重写作者后来编辑的版本；收录不自动跳页、不自动选中。旧笔记模拟的旧改稿建议在折叠区只读保留，不冒充新版复盘结果。
- 名单确认时可调整该读者本次视角、具体关切、表达方式；仅冻结到本次运行，不写长期画像。推荐后的名单或人物调整均明确标记，历史保留调整值。已有画像、分析与群聊历史不自动迁移或覆盖。
- 公开 AI 创作助手直接接入持久化内容协作 session/message：研究、写作、审稿按消息接力，不再通过旧单助手发送。每位角色完成后先展示可读结果和小标题候选；运行中显示角色、耗时与恢复读取入口。旧对话折叠只读。
- AI 建议先预览，允许作者编辑后放入标题／正文画布；保存由作者完成，不静默覆盖正在编辑的稿件。每次新指令使用最新已保存稿，旧消息和运行仍保留各自快照。
- 受众分析优先生成 6～8 位简短候选，但不再自动收录为模拟粉丝。作者逐位收录；既有和已编辑资产保留。模拟默认三个空槽，可以增加；数量是上限而非推荐配额，相关者只有一位也可以模拟。
- 推荐、采用、调整及实际参与名单分别展示。未采用的推荐不会替换当前选择；手选同样需要明确确认。运行保存当时推荐与最终名单，后续人物修改不污染历史。
- 试读支持创作选题和已导入历史笔记；历史笔记按来源 ID＋note ID 读取，不伪造新选题。读者只看标题／正文，历史指标留作作者参考。只给标题时测阅读意愿和期待，不当成完整正文挑缺失。
- 试读结果采用单左栏群聊：稳定拼装 SVG 头像、统一发言／回复层级、中文名字替代内部 ID。独立反应与互相回应逐位保存并展示，内部试读记录按需展开。打开历史或开始运行时收起准备表单，历史记录横向展示，不占第二个左栏。
- 作者可点名一位或询问所有实际参与读者；追问独立持久化，逐条返回，支持停止等待、错误恢复与显式重发。只给读者原作品、该读者定义和公开讨论，不传同伴的私有试读记录。

中间展示是阶段成果和进度，不是模型隐藏推理；按用户最新决定，角色／读者完成后分段出现即可，不需要逐字流式。历史笔记复盘用于发现理解与表达阻力，不自动证明真实流量的因果。

## 下一阶段设计 受众 Panel 四阶段

新 Panel 推荐和编辑增加一次独立上下文核对：读者只依据当前作品与原人物需要判断相关性，不看初次推荐理由、不为凑人数自动补人；编辑只对照作品检查拟写入文字，未知经历、数量或功能承诺转为待作者补素材。核对失败不返回未核对的原结果。素材入口保持空白，以中性提示收集真实材料，具体缺口解释与原文位置一同展示。成功运行保存核对决定、模型、提示指纹与两次调用用量。该核对依然依赖模型，允许作者手选读者，不修改原人物或旧分析；不是对原文或外部事实真实性的认证。

Panel 编辑反馈区分基于已有材料的改写和需要作者提供的新素材。补素材卡展示具体问题，不预填模型答案；作者输入拟加入稿件的文字后保存提案并预览，确认才更新正文，作者素材随提案保存。新模型输出的素材请求与直接替换稿不得混用。旧记录可读，旧待采用的补素材提案需重新填写素材，不静默认可旧模型补写。新 Panel 的调整清单从有效反馈卡生成，旧非 Panel 结果与已保存历史不回写；这不是事实真实性自动验证。

显式 Panel 试读先记录本篇已满足的需要与仍未解决的问题，再决定是否留言；人物关切不是必须重复提出的台词。模型上下文按阶段精简，历史片段去重且说明截断，不改保存人物。编辑依据当前作品和本轮反应判断修改价值，不把确认式提问自动升级为关键缺陷。触发句改为模型选择冻结片段编号、程序展开原文，旧引文仍兼容。新阅读状态已入库及传给编辑，尚未新增独立界面字段；两位读者的真实两版检查有所改善，但数字判据和建议事实性仍需后续验证。

演示运行可使用任意已保存读者及同组复测，保留真实资产 ID 和当时快照，不再限制为三个固定示例人物。结果明确为固定演示文字，汇总只说明实际保存记录，不冒充真实模型分析；无公开同伴留言不制造回应，关闭讨论、部分失败与暂停恢复保持原流程。旧内置样例仍兼容。

2026-10-04 用户确认“长期用户画像 → 按本篇话题检索并组队 → 个人意见及互相回应 → 当前创作的修改反馈”。具体改造以[四阶段实施计划](audience-panel-four-stage-plan.md)为准：复用已有读者资产、推荐、两轮模拟和历史快照，补试读任务、可追溯编辑反馈、确认采用及同组复测，不推倒重做。2026-10-05 已接通可选 panelTask、推荐指纹与采用核验、任务／内容快照；关闭讨论真正跳过调用，旧请求保持旧行为。结构化反馈、画布中的预览确认采用及受限撤销已完成。同组复测后台、画布确认、历史进度、原记录回看和逐人原文对照已接通。

历史页逐人对照只读取两次冻结记录：理解、态度、公开评论、顾虑、吸引点以及回应分别显示，桌面双列、窄屏单列；按读者 ID 配对，不按返回顺序猜。保留失败、缺结果和未留言的区别，不自动把某个顾虑消失判为已解决。详细区可核对两版稿件和当时保存的模型／系统提示信息；新运行开始记录真实 provider 返回的模型信息，配置回退值单独标记，旧记录不回填。当前是辅助人工判断的只读比较，不是自动胜负评分或完整模型版本配对。

同组复测复用当时实际人物、案例顺序及阅读任务，只换当前已保存的新稿，新运行通过 parentSimulationId 关联上版。人物资产后来编辑／归档不改变这次组队；独立试读不读取旧评价，旧推荐不作为本轮推荐复用。画布先预览人物、任务和稿件，确认才创建；未保存稿不能提交，请求期间继续编辑则保留文字、不自动跳转。相同请求只创建一次，浏览器会话内按来源和版本保留请求标识；版本过期、归档稿、内容未变或旧快照缺失时明确提示。历史自动刷新进行中的复测，可回看原记录，查询失败不重建。首版只支持新版 Topic 试读，页面明确模型／提示版本尚未配对，不能将差异全归因于改稿。

公开模拟准备页现已支持自然全文试读／定向试读，默认自然全文、开启互相回应；定向填写一至两个问题，每个最多 300 字。改任务取消旧推荐的采用状态、保留手选名单，推荐回执按任务隔离；换账号或选题恢复默认，不把上篇问题沿用到下篇。历史详情按运行快照展示当时方式、问题和讨论开关，与推荐／实际读者名单一起回看；缺字段不补造，开启不冒充执行成功。不把全文试读称为标题点击预测。

新的 Panel 反馈必须经过作者选择及确认才能改稿；此范围不包含改变现有普通创作对话的自动应用方式。画像仍优先 8 位、通常 6～8 位并自动保存有效角色，模拟默认三个槽位且可新增，不恢复旧原型确认流程，不引入图片理解或真实触达预测。

Panel 提案现支持受限撤销：在已采用的前后对照中二次确认，只有当前稿仍为该次采用版本才恢复修改前标题正文。恢复产生新版本，采用回执和撤销回执分别保留；重复操作不重复改稿，后续人工编辑、其他提案写入或归档时拒绝覆盖。未保存内容和等待期间新编辑继续受保护。已撤销不是未采用，历史明确区分；不支持多步回退或重做。

Panel 待确认改稿提案已接入创作画布的“试读反馈改稿”，历史页保持只读。一条有效局部建议可生成包含修改前后文本的提案，明确替换／前插／后插以及具体内容，生成不改稿、不调用模型；明确确认后才原子写入正文及应用回执。重复创建或采用不重复改稿，旧版本、归档稿件及跨账号操作被拦截；原标题正文外的内容与模拟历史不变。已保存提案可刷新或重新进入恢复，未保存稿及正在处理的画布不能采用或撤销；等待期间继续编辑、切换账号或选题不会被旧回调覆盖。首版不支持全文／大纲直接改稿或批量合并，未保存的提案输入不跨关闭恢复。

新协议汇总中的 editorFeedback 区分读者依据与编辑额外建议，记录原文锚点、来源发言、受益读者、取舍及可选改写。来源必须来自当次有效反应／回应，局部引文必须匹配冻结标题或正文；程序保存出现序号、Unicode 字符坐标与内容指纹。内部试读感受不冒充公开评论，额外建议仅为可选。无效条目剔除并留诊断，旧字符串建议仍可读；这里只校验可追溯性，不保证模型判断正确，也不写入正文。

读者驱动的修改卡现在必须关联当次 concerns／newConcerns 中记录的具体顾虑，并保存原始顾虑及来源；空目录不等于真实读者毫无问题，也不禁止编辑提出可选创意。认可反馈继续可用。缺记录、错消息或伪造的顾虑引用逐条拒绝，不静默变成已确认需求；旧保存结果保持可读。该约束只覆盖结构化反馈卡，不代表旧自由文字总结已获得同样的归因保证。

为避免模型将读者评论误抄成正文，新汇总的局部定位改为从程序生成的冻结原文片段中选择编号，再由程序展开为既有引文和坐标；旧历史无需重写。片段目录限长且明确标注未覆盖，整篇、跨片段或大纲可用全文建议，不猜定位。实测已验证编号定位可行，但读者需求与编辑推想的归因仍待改进，不能把引文通过视为建议语义通过。

模拟结果与历史现展示“值得保留／关键调整／其他可选建议”卡片，可展开当次来源及原文高亮；可选项默认折叠，无来源或不匹配原文不拿当前资产补造。无有效卡保留旧字符串建议，并区分未返回、无效与未生成具体卡片；风险提醒继续显示。卡片只读，不提供自动改稿或采用入口；界面组件与窄屏／键盘检查通过，真实模型反馈效果待验收。

修改卡现在直接展示经当次来源核对的具体顾虑，内部顾虑与公开原话分开标记。同一顾虑集合、相同原文位置和优先级的多张卡放在“同一问题的多种改法”下，保留每张完整建议，可择一或自行组合，不表示必须全部采用。旧字段缺失、无法核对或不同位置不强行归组，编辑可选建议单独保留；没有写稿动作。

## 下一阶段设计：账号复盘与人机共创（计算底座已增量实现）

内容生成的新设计见[账号复盘与人机共创](creator-writing-collaboration-design.md)：从多指标笔记比较提炼可选择的写作经验，创作者在现有画布中与固定的研究、写作、评审角色协作，讨论角度、起草和定向修改。消息由 LangGraph 父图串行执行，角色可结构化地点名下一位，确定性 dispatcher 校验路由；协作会话冻结当前 Topic 与工作区上下文，角色消息追加保存，运行回执保存待投递消息和回合状态。协作默认使用 Qwen specialist provider；本地确定性 demo 仅在显式选择时使用。每位角色获得不同的任务包，并以稳定候选 ID 承接上一角色的结构化结论和引用，而不是只共享一长段聊天记录。无论模式都不允许协作角色直接写入 Topic 或 Draft，采用仍走现有确认边界。外部 Skill 只借鉴方法，不直接安装或套用预置人格、行业阈值。

当前画布仍编辑 Topic，AI 合法修改仍按现有规则自动应用；历史修改已有只读前后对照，采用／撤销、选区改稿工具、经验选择与长期风格偏好尚未实现。“首次起草直接填入、已有正文先确认”的默认值是待确认方案，不是本轮行为变化。现有读者确认与模拟入口保持不变。

创作发送链路在保存、创建对话、发送消息、读取新稿之后检查当前画布是否仍有效：切换账号／选题后，不再推进旧页面回调和未发出的后续请求。保存或创建对话期间又改稿，会保留新文字并暂停发送，请用户确认后重发；已经发送后继续改稿，也不被返回结果覆盖。成功返回只清空本次提交的消息，不清空等待期间新写的下一条。前端防止同一轮重复提交，但这不是取消后端已接受的任务，也不等于网络失败后的人工重试一定不产生新模型调用。

2026-10-04 创作记录增量：新产生且通过输出校验的 AI 修改，在助手消息元数据中保存 `canvasEditSnapshot`，包含所属账号／Topic、执行前标题正文及版本、建议标题正文、实际应用后的标题正文及版本。与 Topic 更新同事务保存；版本冲突时保留原基础和建议，after 为 null。后续手工编辑不改这份历史，同请求重放返回原记录；模型失败、事实未通过或仅讨论不冒充已应用记录。已有消息不回填，生成快照不变，无新表或新接口。创作对话现已加入默认折叠的只读对照：成功展示修改前／当时应用后，冲突展示修改前／未应用建议；建议与实际结果一致时不重复展示。旧记录缺快照明确提示，不拿当前稿件补造；跨账号或选题的快照不显示正文。采用／撤销仍未接入。

新账号诊断现已保存四项互动指标的独立汇总和逐条排名：各指标分别计算有效样本、中位数和缺失数，缺失不当零、并列同名次，不生成统一质量分或没有数据支持的互动率。旧点赞字段与历史兼容保留，旧记录不回填。结果页的“笔记表现”现可切换点赞、收藏、评论和分享，显示当前指标的有效数据数、中位数与缺失数，并打开当次笔记正文。无点赞也能查看其他指标；旧历史缺汇总时仅按原快照数字计算展示，不读取当前资产补造历史。同值笔记不会分到高低两组，各组最多展示两条。模型尚不读取新增汇总，不表示独立复盘经验卡已生成。

带 observations/v1 的结果页不再在“更多内容归纳”重复显示模型生成的高低表现、metric 和原因共性，数值比较统一由“笔记表现”呈现。创作建议仍单独保留为“可尝试的写法”，不冒充已验证结论；同名笔记按 ID 回看。不含 observations 的旧报告保留可读，历史 JSON 不重写。

选题阶段现进一步分离数值与归纳：有结构化小红书快照的账号诊断，只传内容归纳、writingSuggestions 和从当次所选笔记计算的 performanceObservations，不传模型 contrast 的高低表现／指标／共性。暂停后恢复也使用原运行快照，不取最新资产；原分析结果和已生成选题不变。上文“模型尚不读取新增汇总”仍适用于画像 PROFILE；选题 TOPICS 现在读取此确定性汇总。旧纯文本路径兼容保留，其他自由文字的数字未做语义核验，也不表示所有直接 skill 或创作入口都已完成同样隔离。

账号复盘的 prompt 现补充“先认识账号、比较具体笔记、拆解写法、给出带适用场景的调整”，沿用原结果字段，不改变页面或自动存储规则。新增经验仍是 contrast.takeaways 的文字建议，不是可采用的独立经验卡。最新一次同冻结输入检查在 84.35 秒完整返回，建议包含具体来源和调整，但跨场景归纳与低互动原因解释仍有问题；受控前后对照因此前基线超时未完成，不能把工程回归或一次成功返回视为模型质量已验收。新增诊断显示本次时间集中在响应头之前，正文读取及解析约 4.44 ms；尚未拆分网络、排队和生成耗时，不自动重试或全局延长超时。

创作助手 prompt 已区分讨论、起草、定向改稿和风格检查，定向请求要求保留未指定部分。两次真实构造样本检查中，只改开头保留了标题／其余段落／换行；先讨论返回不同角度且不更新正文。它仍返回原结构、沿用现有自动应用与版本冲突保护，没有新增采用／撤销或服务端自然语言范围判定；不能将单次成功当成所有局部改写都不会越界。首稿、标题修改与风格检查目前只完成注入响应回归，真实质量待验收。

2026-10-04 画像增量：提示要求先区分共同写法与具体经历，缺失互动数省略或显示未提供；没有内容依据时不填低互动原因，改为有目标的尝试建议。保持积极、具体的反馈，不因互动少贬低记录型内容。研发检查新增连接／TLS／发送／接收事件时间线，仅本地报告可见，无生产等待时间、自动重试或历史结构变化；本地验证不代表新提示已通过真实内容质量验收。

## 按当前选题推荐读者：主模拟页已接入

内置“直球行动派”现在以条件判断而非固定追问描述人物：能自行开始就愿意试，确有外部参与门槛但缺入口才询问。只影响新派生声音，已有粉丝与模拟快照不自动升级。一个新派生角色的两次实测分别表现为自助场景不留言、招募场景询问入口；这是局部行为验收，不是全部受众生成质量通过，原角色的既有失败结论仍保留。

2026-10-04 效果检查补充：同一已有行动型角色面对不同报名条件的两次 Qwen 独立反应中，能在理解字段区分自助与招募，但自助场景仍追问已明确无需的报名入口。结构及引用通过不等于人物适配正确；当前仍有把角色习惯执行成固定动作的问题。诊断支持固定人物和历史案例的配对场景，不增加用户入口，也不自动调整或覆盖已编辑人物。

2026-10-03 讨论形成下一步方向：账号受众分析建立可编辑的读者池，选题确定后再从本账号已有读者中推荐相关且有判断差异的一组人，用户仍可换人或继续增加槽位。不为每个题目重写人物，不只选赞同者，也不强制造成对立。推荐理由给创作者查看，不成为模拟角色必须执行的反应指令。

主模拟页已加入显式“推荐读者／使用这组”，先选题、预览正文，再推荐和选人。初始槽位仍按列表填前三位，随后保留手动选择；进入页面不自动调用模型，推荐返回也不替换名单。后端已接通真实 Qwen、SQLite 记录、独立执行及创建／查询接口：本账号全部有效编辑卡片进入，未知／重复 ID 和人物重写被拒，有说明的无匹配可完成。输入超过 64 KB UTF-8 预算明确失败、不截池，空池不调用模型；配置缺失返回 503，不在生产返回演示推荐。同 key／同请求重放原记录，即使人物已编辑；刷新和响应丢失不重复执行，结果不随资产编辑改写，中断不自动重发。存量 5 人池两题实测已完成，部分推荐理由仍有预设动作，后续提示调整尚未复测。

后端返回推荐的实时过期状态，并在创建模拟时同事务重新核验：正文、定位或完整候选池变化不能混用旧推荐，原结果仍可读；置顶及内部创作角度不影响有效性。页面在“使用这组”时再读取核验，合法的少量推荐保留空槽，不补造读者。采用后允许手动换人和增加槽位，提交原推荐 ID／指纹及最终名单；模拟快照保存建议、实际名单及 manual／recommended／adjusted 来源。失败、无匹配或过期时保留手选，已采用者可明确解除关联继续手选模拟。推荐理由不进入模拟模型。

浏览器按账号和选题保留请求回执；刷新只读已存在任务，没有拿到任务 ID 的请求必须手动重试原请求，不因页面恢复重新付费。当前只恢复推荐记录，不恢复未提交的槽位或“已采用”状态。公开版的分析选题卡、选题库和 AI 创作助手已汇聚到同一个模拟确认页：入口不创建运行，用户确认后点“开始模拟”才执行。创作助手的“选择模拟读者”先保存当前标题和正文；保存失败保留编辑、不跳转，保存等待中禁止继续编辑或重复提交，切换选题／账号后不响应旧保存结果。未修改的正文直接使用当前保存版本。页面之间导航保留同账号已手选的读者，换账号不带入旧目标。

公开 AI 创作助手编辑的是 Topic 的标题／正文，不是独立 Draft。独立 Draft 页仍在内部工作台，保留原兼容模拟路径，不为统一入口重新开放给公开用户。历史页现已并列显示当时推荐与实际参与人选，区分使用推荐、调整推荐和手选，理由默认收起。新运行冻结推荐者姓名（包括未选用者）；旧记录缺姓名或来源时明确提示，不读取当前粉丝资料补造。未生成角色时显示“本次选择”，名单不代表每人都已完成反应，执行情况仍见阶段结果。内部 Draft 推荐确认不是当前公开版阻塞项。字段和分步验收见[模拟粉丝设计稿](simulated-fan-model-design.md)。

同一账号不同经历可以共同体现创作优势，但不应混成一段经历：例如求学导师的关心和公司带教的成长安排，可以共同说明写具体支持过程的能力，不能合写成实习团队的特点。画像提示已补此区分，仍保持积极表达；最新一次真实复测仍发现学校经历用于职场优势，跨场景混淆尚未解决。研发检查支持冻结输入重放，原始输出与实际保留字段分开留存。

账号画像按实际可用字段展示：缺少概要时仍保留关键词与优势；仅有优势或有效近期变化时不留空白介绍卡。完全没有可展示画像时如实提示，不把引用过滤或生成失败归因于笔记不足。依据长文本允许换行，窄屏卡片随可用宽度收缩，不截断原文；已有笔记数据、历史引用和详情浏览保持不变。该展示行为已用真实结果和边界样本检查，不表示模型缺失字段已经修复。

关键词与优势的“查看依据”按不同笔记计数，同篇多段引文保留但不重复展示卡片，例外笔记同样处理。回看始终使用该次分析的正文快照；快照缺正文时保留历史结论与引文，明确提示不能回看完整笔记，不用当前账号资料补造。笔记表现中缺正文的入口禁用。切换分析关闭旧笔记详情和展开区，封面只从该次分析所属工作区取用。已有正文快照不因当前素材删除而失效，不回写历史。

研发侧新增只读账号画像检查脚本，与实际诊断共用模型输入整理逻辑，默认不调用模型；显式验证仅请求一次画像，不创建正式运行或选题。结构／引用通过与人物化表达、优势具体性等内容验收分别记录。一次 QSheep 真实请求在调用层失败，尚未形成可评价输出；本增量是检查能力，不代表画像生成效果已经改善。

检查脚本现可记录分阶段响应诊断与脱敏后的模型正文，用于区分接口、解析和结构问题；只进入本地检查报告，不新增用户界面或生产历史字段。假响应回归通过不等于已确认上一次真实失败原因，也不触发自动付费重试。

一次后续实测确认账号画像在 3400 token 额度处被截断。现将该操作额度提高到 6000，其他操作额度不变；Qwen 报告 length 时明确失败，不将可解析的残片当作完整画像，也不自动重试。新额度下单次检查已完整返回，但实际输出只有 3310，不能独立证明容量变化的效果。模型拼接引用仍导致概要等字段被过滤；已补短连续引用示例，未放宽校验或改写旧结果，该提示效果尚待真实验证。

## 2026-10-03 增量：选择模拟粉丝时预览人物

受众模拟中，每个已选粉丝下显示其已保存的兴趣、具体需求和人物特点，不必离开当前页面查看档案。默认收起长描述，展开后显示全文、内容偏好及表达方式；未选槽位不显示预览。切换角色重置展开状态，旧角色没有兴趣字段时不猜填。已归档或找不到的选择提示重新选择，不展示失效画像；维持默认三个槽位、可继续新增及同一人物不可重复选择。预览不修改资产，也不改变运行时的快照规则。

## 2026-10-03 增量：沉默与执行缺失分开

受众模拟汇总现在接收由程序计算的讨论概况：哪些角色完成第一轮但不评论、哪些角色可看到他人公开评论、哪些已选择不回应，以及哪些确实没有执行结果。沉默不当成失败，完整正文不称为仅标题的概念预演；旧历史结果不回写。建议与风险仍使用兼容的字符串数组。角色反应和执行概况属于输入事实，汇总的额外创作建议不应冒充已出现的读者问题。

同题受控案例已验证行动、查证、安静角色可以出现不同参与行为，但汇总仍可能超出输入补充建议、泄露内部术语，行动角色也可能编造具体未来情境。当前实现不是稳定的人群预测器，语义边界尚有待打磨；实际检查与下一轮计划见[状态记录](status-and-todo.md)。

## 2026-10-01 增量：宽兴趣与具体人物

模拟受众不再以单篇笔记的话题充当人物定义。新增兼容字段 `interests: string[]`，用于“留学、职业发展、个人成长”这类能跨笔记复用的宽兴趣，生成目标 1～3 项，API 与编辑最多 6 项、每项 30 字。旧结果缺失时按空列表读取，不自动补写或迁移历史。兴趣不限制这个人只能读这些话题，也不代替本次具体需求。

`profile` 用一句话描述遇到什么内容后如何判断或行动；`coreConcern` 写想获得的具体帮助或要做的决定；`contentPreference` 只描述希望看到的内容形式；`expressionStyle` 描述说话和参与方式。比如共享“留学、个人成长”兴趣的两位读者，可以分别需要“确定本周第一步”和“判断这条路径是否值得尝试”，前者等到步骤、成本清楚才行动，后者先找相似起点的案例。不确定哪种性格成立时可以各刻画一位合理角色，而不是把全部可能性塞进一个模糊人物。仅换语气、要求角色强行争论或用角色数量代表真实人群比例，都不属于本次目标。

兴趣在分析短卡片和粉丝资产中可见，粉丝详情可编辑并显式保存；派生声音保留源粉丝兴趣。创建模拟时把当前兴趣与人物定义一并冻结，独立反应和第二轮交流使用同一份快照，不在运行中读取后改的资产。旧客户端不提交兴趣时保留原值，明确提交空列表才清空；旧分析、原始定义与历史模拟不覆盖。

验收除了字段校验、保存重开和两轮输入传递，还需人工比较同兴趣角色：需求是否具体、判断依据和行动是否真有差别，且不只是把原笔记标题换个名字。每轮仍优先 8 位、通常 6～8 位，全部有效角色自动保存。2026-10-02 起已做小规模真实模型检查，结果与剩余问题见状态记录，工程通过不代表实际生成已经稳定达到质量目标。后续 `facets` 多维表单与“候选匹配后人工确认”的设计尚未接入，不是当前自动保存的前提；详见 [模拟粉丝设计稿](simulated-fan-model-design.md)。

## 2026-10-01 增量：更多简短受众角色

每次受众分析优先提出 8 位、通常 6～8 位模拟受众，同一关注点可以组合不同态度、性格和说话方式。每位只需名称、一句话人物特点、一个关注点、简短内容偏好和说话风格；提示词目标分别为名称 4～12 字、简介约 40 字内、其余各约 25 字内，不引入多维表单。材料极少或部分引用无效时允许更少，不强制补齐。页面默认展示短卡片，原文依据和分析说明折叠。模型原始输出保留在运行历史，不通过截断改写旧资产。

每次新分析的全部有效角色自动加入该账号的模拟粉丝列表，不再仅在首次保存前三位。同一分析、同一分组重复保存复用已有资产；下一次分析追加自己的角色，不覆盖已有角色的编辑或归档。用户仍默认选择三位参加模拟，额外角色可在下拉框选择或新增槽位。

## 2026-10-01 增量：模拟粉丝选择槽

受众模拟默认显示三个粉丝槽位，每个槽位用下拉栏选择当前账号的一位未归档模拟粉丝；前三位默认填入已有资产，但可改选或留空。点「＋ 新增」继续增加槽位，额外槽位可移除。至少选择一位才能运行，同一粉丝不可重复选择；不再设三位上限。创建运行时按槽位顺序冻结所选粉丝，旧历史与旧 API 兼容。账号没有足够粉丝时仍显示三个空位，不用话题分组临时伪造粉丝。

模拟粉丝资产页新增「添加不同声音」：以已保存的一位粉丝为来源，选择 12 种内置人物声音中的任意多个，一次创建多个可编辑粉丝。每位继承相同的受众关注点和来源引用，但有不同的判断、表达与参与习惯；这些是 demo 人物设定，不是另一批模型分析分组。按来源粉丝和模板去重，重复添加不会覆盖用户编辑；旧粉丝和模拟历史保持不变。新增角色可在模拟槽位中选择，反应和讨论提示词会读取它们的差异。

## 2026-09-29 增量：诊断材料逐条选择

账号诊断的范围弹窗复用“我的笔记”的封面卡片和详情浏览。默认最近 10 条，用户可以用时间范围快速选择，再逐条增减；卡片可打开正文和已抓取评论，勾选区域独立于详情入口。显示已选数量，支持全选和清空；完成前不改现有范围，取消不保存，零选中不可开始。

提交时携带当前档案及选中笔记 ID，由服务端验证归属和有效性，仅以所选笔记及对应评论生成输入快照和上下文。手动范围标记为 `custom`，保留实际 ID、数量及来源；不得混入全量账号总结。切换账号时重置选择，旧运行输入不受后续编辑影响。本轮只升级账号诊断；受众分析仍使用原有快捷范围，后续可复用同一组件。

## 2026-09-29 增量：受众分析部分成功与诊断

受众分析按分组独立核验原文证据。任何一条引用来源或原文不匹配，整组不参与下游；其他有效分组仍保留，状态为“部分完成”，可继续保存模拟粉丝、进行模拟。全部分组无效则失败。页面允许查看未通过分组与对应引用的错误类别，不把被拒绝内容呈现为已验证结论。

模型结构化原始输出与模型信息须在核验前保存到分析记录，诊断包含分组、引用序号与失败原因。原始输出保留在本地数据库，不进入常规列表响应。旧失败记录不具备这些信息，不补造；刷新或重开不得自动重试付费调用。部分结果的总摘要改为有效分组计数，模型原摘要只留在原始输出中。此处只保证引文来自输入，不保证人物推断或模拟具有现实准确性。

## 2026-09-28 增量：模拟粉丝

09-29 增补：支持开发侧显式预存有来源的阅读角色，复用来源分析记录和粉丝资产，不在启动时为所有账号灌入样例。预置整理必须标明来源类别和未调用模型接口，引用须匹配该账号材料；人物偏好与表达习惯按模拟假设处理，不因引用匹配而升级为实证画像。重复导入保留用户编辑和归档状态。首批仅为 QSheep 预存五类角色，不跨账号复用，也不把预置内容作为 live 失败时的替代响应。

模拟粉丝是账号隔离的可复用内容资产，而非可配置的平台 Agent。受众分析是来源研究记录，粉丝档案是用户选择和调整的阅读视角，模拟运行是该档案阅读某个选题/正文的执行历史。关系为：账号 → 受众分析 → 模拟粉丝；选题 + 所选粉丝 → SimulationRun。

每份档案保存稳定 ID、所属账号、来源分析及分组 ID、不可变原始定义（含引用、历史案例与未知项）、可编辑定义、active/archived 状态和创建/更新时间。用户可编辑名称、兴趣领域、人物特点、关注点、内容偏好、表达习惯；保存需提交预期更新时间，过期编辑返回冲突而不是覆盖。

在粉丝列表内切换角色时，未保存修改需通过弹窗选择继续编辑、放弃修改或保存并切换；未改动时直接切换。保存中禁止重复操作，更新失败或版本冲突保留当前输入，不跳到另一角色。更新成功但列表刷新失败时明确显示“已保存，列表暂未刷新”，保留已确认版本，仅重试列表读取；待刷新成功再完成切换，不重复写入。恢复期间的后续编辑仍是未保存内容，刷新不覆盖它。归档使用同一恢复路径。此保护目前不覆盖离开页面、切换账号和浏览器刷新。

“添加不同声音”收到成功响应后保留返回的角色与 ID，随后列表刷新失败时显示角色已加入，仅重试读取，不再次创建。关闭弹窗后通过“查看加入结果”恢复；原角色已有后续编辑时，刷新完成也不自动跳转或覆盖输入。创建错误与原角色保存错误分开显示，请求中禁止重复操作，关闭后焦点返回入口。回执只保留在当前页面会话中，重新打开页面仍从数据库读取资产；未收到创建响应的网络异常沿用服务端去重处理。

新分析完成时，自动保存本轮所有有效角色；同一来源重复保存不覆盖人工调整。历史分析升级时不自动回填，也不自动执行模型。列表默认不展开详情，用户选择后编辑，归档角色可恢复。模拟时默认提供三个槽位，但可按需增选未归档角色；后台检验账号归属、重复 ID 和状态，并将定义、来源、更新时间及原始证据冻结到运行输入快照。人工设定不等于实证观察；模拟评论不能写回来源证据。

新增 SQLite 表 `simulated_fans`，不增加文件存储或版本表。API 为 `GET/POST /api/workspaces/{id}/simulated-fans`、`GET/PATCH /api/simulated-fans/{id}`；创建参数是来源分析和分组，更新只接收可编辑字段及状态。现有模拟创建接口新增 `simulatedFanIds`，与旧 `audienceAnalysisId` 互斥；旧接口和历史记录继续可用。

## 1. 产品定位

创作者工作区是一个面向创作者运营、内容策划和账号增长分析的内部共创工具。

它的核心目标是把分散的创作者材料、账号分析、热点分析、选题、内容结构和受众模拟沉淀成可复用资产，并通过一组产品内置的 skill、agent、workflow 帮助用户反复调用这些资产。

当前产品不是：

- 通用 agent builder；
- 通用 workflow editor；
- 文件系统或 VS Code clone；
- plugin marketplace；
- 多租户 SaaS；
- 任意代码执行平台。

## 2. 目标用户

### 2.1 创作者运营

典型场景：

- 判断一个账号或视频博主是否值得重点运营；
- 判断创作者是否适合某个激励计划；
- 将单个创作者的材料、诊断结果、选题和模拟沉淀为可复盘资产。

### 2.2 内容策略 / 选题策划

典型场景：

- 基于历史笔记和评论区提炼账号定位；
- 基于热点 CSV 找内容机会；
- 将分析结果转化为选题库；
- 对选题生成内容结构；
- 用受众模拟判断选题是否有传播和转化潜力。

### 2.3 产品 / 研发维护者

典型场景：

- 维护内置 skills、agents、workflows；
- 通过 Capability Maker 生成能力资产 proposal；
- 检查 prompt、上下文输入和 workflow 输出是否符合产品语义；
- 后续把更多固定能力转成可组合资产。

## 3. 核心问题

当前产品解决的问题：

1. 创作者相关材料分散，难以沉淀为可复用资产。
2. 账号诊断、热点分析、视频质量判断、受众模拟之间缺少统一的资产连接。
3. LLM workflow 如果只靠前端临时输入，刷新后难以恢复，也难以复盘。
4. 后续新增能力时，如果所有逻辑都写死在单个页面里，功能会越来越难维护。
5. 用户不应该被迫填写复杂表单；更适合通过 agent 帮用户把自然语言材料整理成结构化资产草稿。

## 4. 产品原则

### 4.1 资产优先

所有重要输入和输出都应该成为资产，而不是只存在于一次页面状态中。

内容资产包括：

- 用户输入类资产；
- workflow 输出后可复用的结果资产。

能力资产包括：

- skills；
- agents；
- workflows；
- conversations；
- proposals。

创作类对象的划分原则：

- Topic、Content Brief、Content Structure、Draft、SimulationRun 是内容资产；
- 生成 Brief、生成结构、改写、润色、基于模拟反馈修订，是能力资产；
- 前端按钮可以直接触发这些能力，但按钮不是资产本身；
- 能力资产 catalog 必须能解释这些按钮背后调用的是哪个 skill / agent / workflow。

### 4.2 产品特定，而非通用平台

资产类型、workflow、agent 和 skill 都围绕创作者内容运营场景设计。

例如：

- 账号概况；
- 历史笔记；
- 评论样本；
- 趋势数据；
- 视频创作样本；
- 账号诊断；
- 热点分析；
- 视频博主质量诊断；
- 受众模拟。

不设计用户自定义任意 asset schema，不设计通用文件树。

### 4.3 广义上下文视野

Context Access Layer 的默认理念是给 agent 尽可能完整的产品视野，而不是过度保守切分。

约束不是“少给信息”，而是：

- 只从已知产品资产读取；
- 每段 context 都有 asset ref；
- 记录 snapshot 和 content hash；
- 对过长内容做 summary/omitted 记录；
- 不读取任意文件路径或 secret。

### 4.4 用户确认写入

用户编辑和模型生成必须分开：

- 模型生成的是 generated snapshot 或 proposal；
- 用户编辑的是 editable content；
- agent 自动整理输入时只填草稿，不静默覆盖已有资产；
- proposal 需要用户确认 apply/reject。

### 4.5 刷新安全

workflow 执行不应依赖前端连接。

当前约定：

- POST 创建 run；
- 后端 worker 执行；
- 前端观察状态；
- SSE / polling 只负责观察，不负责启动执行；
- run、stage result、stage error、input snapshot 必须持久化。

### 4.6 Live 能力必须可单独验证

真实模型调用不应该只能通过前端手工点击验证。当前要求是：文本模型、agent conversation schema、media skills 都必须有独立 smoke script，可以在不打开浏览器的情况下验证后端配置是否可用。

这件事的产品意义是降低 PM 调优时的不确定性：如果 smoke test 通过，前端问题更可能是 UI、输入绑定或 workflow 组装问题；如果 smoke test 失败，应优先修复 provider 配置，而不是修改产品逻辑。

## 6. 核心资产模型

### 6.1 Workspace

当前前端隐藏 workspace 创建和切换，系统自动使用默认 workspace。

字段：

- `id`
- `name`
- `accountPositioning`
- `positioningVersion`
- `currentTopicId`
- `createdAt`
- `updatedAt`

产品含义：

- 当前顶层数据容器；
- 暂时不是正式用户管理机制；
- 后续仍可作为本地项目或创作者集合容器。

### 6.2 输入内容资产

输入内容资产是 workflow 的主要输入来源。

当前类型：

| 类型 | 用途 | 存储 |
| --- | --- | --- |
| 创作者档案 | UI 上层入口，不是单独数据库表；聚合小红书主页、账号概况、历史笔记、评论样本和视频创作样本 | 由下列 input asset 组合 |
| 小红书创作者主页 | 本地爬取后解析出的主页、笔记、评论、互动和封面引用 | SQLite JSON text + 关联 MediaAsset |
| 账号概况 | 创作者档案子类；账号/创作者定位，可用于多个 workflow | SQLite text |
| 历史笔记 | 创作者档案子类；账号历史内容、标题、数据表现 | SQLite text |
| 评论样本 | 创作者档案子类；评论区痛点和用户表达 | SQLite text |
| 视频创作样本 | 创作者档案子类；视频创作者背景、视频样本、运营备注 | SQLite text |
| 趋势数据 | 热点内容数据，当前通过 CSV/TSV 上传 | 文件落盘 + SQLite metadata/preview |
| 图文素材 | 主页截图、封面图、评论区截图、视觉参考 | 文件落盘 + SQLite metadata/derived JSON |
| 视频素材 | 样本视频、视频参考、后续视频诊断输入 | 文件落盘 + SQLite metadata/derived JSON |

创作者档案页需要展示一个组合概览，聚合当前选中的小红书主页、账号概况、历史笔记、评论样本和视频创作样本，并展示 ready/missing 状态。当前这是前端组合视图，不创建新的 `creator_dossier` 表，也不改变现有 input asset API。

能力：

- 列表；
- 详情查看；
- 新建；
- 显式保存；
- 另存为；
- 趋势数据上传和 preview；
- 小红书离线导入包上传，生成结构化主页资产和封面图文资产；
- workflow 运行前自动保存当前必要输入；
- 输入素材整理 agent 生成草稿。

资源管理页的选择规则：

- 左侧进入“创作者档案”或任意 input asset 子类时，不自动打开 workflow 当前默认选中的实例；
- 右侧详情区先显示空态，要求用户从左侧实例列表中显式选择，或点击新建；
- workflow 页面仍可以保留默认输入选择，用于直接运行；
- 资源管理页的显式选择和 workflow 输入默认值是两个不同概念，避免用户以为进入资源页就已经在编辑某个资产。

媒体资产当前实现：

- 上传；
- 列表；
- 详情预览；
- metadata JSON 编辑；
- derived JSON 编辑；
- 用户备注；
- Context Access Layer overview；
- 本地视频预览抽帧；
- Qwen 图片理解；
- Qwen 视频理解；
- Qwen 图片生成；
- Qwen 视频生成。

图文素材和视频素材页采用“左侧列表选择，右侧展开详情”的交互：

- 上传图片 / 上传视频是列表中的动作项，点击后在右侧展开上传表单；
- 生成图文素材 / 生成视频素材是列表中的动作项，点击后在右侧展开生成表单；
- 选择已有素材时，右侧展示该素材详情、预览、理解草稿和保存入口；
- 不在右侧默认平铺上传和生成表单，避免管理页信息过载。

Qwen 理解结果先展示为草稿，用户确认后才写入 `MediaAsset.derived`。生成类 media skills 会把远程结果下载到本地受控 media storage，并登记为 `MediaAsset`。Demo 模式下媒体理解/生成必须明确标识为 demo；Live 模式才调用 Qwen。

当前仍不做：

- 独立 OCR / ASR 流水线；
- 本地上传视频文件直传给 Qwen；
- 视频平台链接抓取、平台数据抓取或长视频语义切片。

### 6.3 分析结果资产

由 workflow 生成并持久化。

当前 workflow type：

- `account_diagnosis`
- `trend_analysis`
- `video_creator_quality`

AnalysisRun 生命周期：

- `pending`
- `running`
- `completed`
- `partially_completed`
- `failed`

保存内容：

- workspace ID；
- workflow type；
- immutable input snapshot；
- stage results；
- stage errors；
- model metadata；
- review status：unreviewed / useful / rejected；
- user notes；
- timestamps。

编辑边界：

- `reviewStatus` 和 `userNotes` 是人工复盘元数据，可以通过 optimistic lock 显式保存；
- `inputSnapshot`、`stageResults`、`stageErrors` 和 `modelMetadata` 是不可变执行历史，前端只读展示。

### 6.4 选题资产

Topic 来源：

- 账号诊断；
- 热点分析；
- 手动创建。

字段：

- title；
- angle；
- associated pain point；
- why it fits；
- source analysis run；
- source workflow；
- status：candidate / selected / archived；
- timestamps。

能力：

- 保存到选题库；
- 设为当前选题；
- 编辑标题和角度；
- archive；
- 生成创作 Brief；
- 发送到受众模拟；
- 生成内容结构。

### 6.5 Draft / 创作 Brief / 内容结构资产

当前 Draft 表示由选题生成的创作 Brief、内容结构或用户继续编辑的草稿。系统通过 `kind` 区分：

- `content_brief`：选题对齐后的创作任务说明；
- `content_structure`：可继续编辑的内容结构。

Content Brief 字段包括：

- topicTitle；
- refinedAngle；
- targetReader；
- readerPain；
- contentPromise；
- corePoint；
- formatRecommendation；
- openingHook；
- argumentPath；
- materialNeeds；
- titleDirections；
- cta；
- risks；
- revisionSuggestions。

关键原则：

- generated snapshot 和 user editable content 分离；
- 每次生成都必须有数据库记录；
- 从 Brief 继续生成内容结构时，结构 Draft 的 input snapshot 必须保存 sourceBrief draft ID 和 Brief editable content；
- 不引入版本表；
- 不把 Draft 做成通用文档系统。

### 6.6 SimulationRun

受众模拟从一个 Topic 或手动输入 topic 开始。

保存内容：

- persona definitions；
- initial reactions；
- debate responses；
- synthesis；
- stage errors；
- input snapshot；
- review status：unreviewed / useful / rejected；
- user notes；
- timestamps。

要求：

- persona 是产品内置 runtime role，不是用户可配置 platform agent；
- 单个 persona 失败时保留部分结果；
- 可重新打开历史 simulation；
- `reviewStatus` 和 `userNotes` 可编辑，原始模拟结果和 model metadata 保持只读。

### 6.7 能力资产

能力资产是研发和产品维护者视角下可组合、可编辑、可新增的资产。

#### Skill

当前 skill 是产品内受控能力 contract + 可选后端 invoke 实现。

它不是任意代码工具沙箱。

字段包括：

- skill id；
- display name；
- category；
- purpose；
- trigger intents；
- required inputs；
- optional inputs；
- context policy；
- output schema；
- artifact effect；
- side effects；
- failure mode；
- composable with；
- implementation refs；
- status；
- version。

当前 skills 分两类调用入口：

- 可通过 `POST /api/skills/{id}/invoke` 直接调用：输入素材整理类 skills、Qwen 图片/视频理解与生成类 media skills；
- 可通过 `POST /api/skills/{id}/dry-run` 做无副作用测试：analysis/topic/draft/simulation/video 诊断类 skills 返回结构化样例输出，不创建 AnalysisRun、Topic、Draft、SimulationRun 或 MediaAsset；
- 通过产品入口调用并落库：`topic.refine_to_brief`、`draft.generate_structure`、`draft.generate_structure_from_brief`。

创作输出类 skill 不需要先开放成通用 invoke API。当前更重要的是保持 Topic / Draft 的产品语义：用户从选题触发 Brief 或结构生成，后端创建持久 Draft，generated snapshot 和 editable content 分离。

当前 Skill Test 面板会根据 skill 类型选择 invoke 或 dry-run。dry-run 用于帮助 PM 验证 contract 和预期输出形状，但不代表该 skill 已经具备独立真实执行链路。

#### Agent

Agent = system prompt + 多个 skills + 默认 context policy。

当前内置 agent：

- Creator Dossier Curator；
- Account Diagnosis Strategist；
- Trend Opportunity Strategist；
- Video Creator Quality Analyst；
- Topic and Creative Output Editor；
- Audience Simulation Researcher；
- Capability Maker；
- Creator Dossier Formatter。
- Media Generation Operator。

#### Workflow

Workflow = 多 agent、多 task 的产品任务计划。

当前 workflow asset 是能力目录和调用说明，不是前端可编辑 nodegraph。

核心字段：

- `workflowId`：稳定 ID；
- `displayName`：展示名称；
- `purpose`：用途；
- `entryAgentIds`：入口 agent；
- `agentPlan`：多级 task plan；
- `artifactEffect`：会产生或更新的产品资产；
- `callBinding`：可选调用注册，允许值为 `account`、`trend`、`video` 或空字符串；
- `status`、`version`、`source`、`updatedAt`。

`callBinding` 的含义是：把该 workflow asset 显示到右侧 workflow 调用区，并绑定到已有产品执行入口。它不代表前端可以编辑任意 nodegraph，也不代表后端会按任意 generated workflow plan 自动执行。

能力资产详情需要支持组合关系跳转：Agent 详情里的 skill 引用可以打开对应 Skill；Workflow 详情里的 entry agent、task agent 和 task skill 引用可以打开对应 Agent / Skill。这是 PM 调优路径的一部分，不是通用图编辑器。

当前内置 workflow：

- Account Diagnosis Workflow；
- Trend Analysis Workflow；
- Video Creator Quality Workflow；
- Topic to Creative Output Workflow；
- Audience Simulation Workflow。

#### Conversation

Agent conversation 用于直接和某个 agent 对话。

当前能力：

- 创建 conversation；
- 发送 user message；
- 后端生成 assistant message；
- 支持 demo/live；
- 支持 queued/running/completed/failed 状态；
- 可携带当前选中的 Skill / Agent / Workflow 作为 context target；
- 可产生 AssetProposal；
- conversation 会作为内容资产出现在左侧“对话记录”入口，支持按 workspace 复盘消息、引用资产、model metadata 和 proposed actions；
- 重新打开 conversation 只读取已保存记录，不重新执行模型。
- conversation title 和 status 可编辑，用于重命名、归档和恢复；message content、context pack、model metadata 和 proposed actions 原始记录保持只读。
- 发送消息携带 `clientMessageKey`，同一 conversation 下相同 key 的重试不会重复创建 user / assistant message；
- assistant 占位消息的 model metadata 记录 `queuedAt / startedAt / completedAt`，用于刷新后观察和复盘执行生命周期。
- assistant 生成有独立 `agent_conversation_jobs` 记录，保存 mode、status、attempt count、错误和时间戳；应用启动时会恢复 queued/running job。

#### AssetProposal

Capability Maker 产生的变更建议。

当前能力：

- 保存 proposal；
- pending proposal 可编辑 title、description 和 proposed action JSON；
- Agent / Workflow proposal 的常见字段可用结构化表单编辑，并同步回 proposed action JSON；
- apply 前展示 diff preview，包括 operation、target asset、changed fields 和 validation errors；
- apply；
- reject。

Apply 规则：

- `skill.propose_definition` 创建或更新 Skill；
- `agent.propose_definition` 创建或更新 Agent；
- `workflow.propose_definition` 创建或更新 Workflow；
- payload 可用 `targetAssetId` 指向已有能力资产；
- 如果没有 `targetAssetId`，后端会用 `skillId` / `agentId` / `workflowId` 在当前 workspace 内查找已有资产，命中则更新，未命中则创建；
- stable id 不可通过 proposal 修改；
- 更新已有 builtin asset 时，该 workspace 内的资产会转为 generated override，避免后续 builtin seed 覆盖已经确认的修改；
- Agent proposal 的 `skillIds` 必须引用当前 workspace 已存在的 Skill；
- Workflow proposal 的 `entryAgentIds`、task `agentId` 和 task `skillIds` 必须引用当前 workspace 已存在的 Agent / Skill。

待增强：

- 前端已有 Agent skill checklist 和 Workflow task 表格作为辅助编辑；更复杂字段仍以 JSON editor 为主。

## 7. 关键用户流程

### 7.1 管理输入内容资产

目标：把创作者材料沉淀为可复用输入资产。

流程：

1. 用户在左侧选择资产类型。
2. 页面展示该类型的资产实例列表。
3. 用户选择已有实例或新建实例。
4. 用户直接编辑字段，或把原始文本粘贴给输入素材整理 agent。
5. agent 返回结构化草稿。
6. 用户确认后显式保存。

验收标准：

- 不应静默覆盖已有资产；
- 保存时显示 saving/saved/error；
- 中文内容必须 UTF-8 原样保存；
- 新建资产必须有名称字段；
- 保存后的每条资产实例都可被 workflow 显式选择；
- 进入资源管理页不应自动打开 workflow 当前默认选择的实例；
- 必须点击实例或新建按钮后，才显示对应详情/编辑器。

### 7.2 小红书创作者主页离线导入

目标：把本地获取的小红书主页数据整理为主平台可复用的结构化输入资产，同时保留笔记封面作为媒体资产。

边界：

- 小红书数据获取在主平台外部完成；
- 主平台不访问小红书、不抓取页面、不保存客户端提供的任意本地路径；
- 推荐使用 MediaCrawler 本地输出，经 `scripts/export_xhs_import_package.py` 整理成离线导入包；
- 旧 `xhs-profile-import/v1` JSON / Markdown 仍作为兼容导入路径。

离线导入包结构：

```text
xhs_import_package/
  xhs_creator_profile.json
  images/
    <note_id>/
      0.jpg
```

`xhs_creator_profile.json` schema 为 `xhs-creator-profile/v1`，至少应包含：

- `creator.displayName`；
- `creator.profileText`；
- `notes[].noteId`；
- `notes[].title`；
- `notes[].desc`；
- `notes[].metrics`；
- `notes[].comments[]`；
- `notes[].cover.relativePath`；
- `notes[].cover.caption`。

前端流程：

1. 用户进入内容资产 → 小红书创作者主页。
2. 用户选择离线导入包文件夹。
3. 前端本地读取 `xhs_creator_profile.json` 做导入前预览，不上传文件、不调用模型。
4. 预览展示账号名、笔记数、评论数、图片文件数、匹配封面数和缺失封面数。
5. 如果当前 workspace 已存在同名 `XHS {账号名} 创作者主页`，前端提示默认会更新已有资产。
6. 用户点击更新 / 导入，或选择另存为新主页。
7. 后端接收 profile JSON、图片文件和浏览器提供的相对路径，保存主页资产和封面媒体资产。
8. 导入完成后，前端选中新资产或更新后的资产，并完整展示后端 warning 列表。

后端要求：

- 只接受包内相对路径；
- 拒绝绝对路径和包含 `../` 的路径；
- 浏览器目录上传产生的公共顶层目录前缀应在前端剥离，使路径与 JSON 中的 `images/...` 匹配；
- 主页资产默认命名为 `XHS {小红书账号名} 创作者主页`；
- 封面媒体资产命名为 `笔记标题_封面`；
- 封面 caption 和 user notes 优先使用笔记正文；
- 重复导入同名主页时，默认更新同 workspace 下的已有 `xhs_creator_profile`；
- `saveAsNew=true` 时强制创建新主页资产；
- 封面媒体资产按名称复用，不重复创建同一封面。

详情页要求：

- 优先展示结构化摘要：账号名、笔记数、评论数、封面引用数和高互动前 5 条；
- 保留原始 JSON 编辑区，用于检查和必要的人工修正；
- warning 必须完整展示，不只展示第一条。

验收标准：

- `_tt` 导入包可生成 `XHS 秀***冰 创作者主页`；
- `QSheep` 导入包可生成 `XHS QSheep 创作者主页` 或脱敏 nickname 对应名称；
- 选择文件夹后无需上传即可看到本地预览；
- 导入后能看到结构化摘要和完整 warning；
- 重复导入默认更新已有主页资产，不增加重复列表项；
- 选择“另存为新主页”时会创建新资产；
- 封面媒体资产保留 `笔记标题_封面` 命名和正文 caption；
- 后端测试覆盖创建、默认更新、另存为新、路径逃逸拒绝；
- 前端测试覆盖本地预览、同名提示和 warning 列表。

### 7.3 账号诊断 workflow

目标：基于账号概况、历史笔记、评论样本生成账号诊断和选题。

输入：

- 账号概况实例；
- 历史笔记实例；
- 评论样本实例；
- demo/live mode。

执行：

1. 用户在右侧选择账号诊断。
2. 中间页按输入源逐项展示选择器和预览。
3. 用户点击生成。
4. 前端自动保存当前必要输入。
5. 后端创建 AnalysisRun。
6. 后端 worker 执行 workflow。
7. 前端观察 progressive stage results。
8. 结果进入分析结果历史。
9. 生成的 topic candidates 可保存到选题库。

输出：

- profile analysis；
- pain points；
- topics；
- stage errors；
- persisted AnalysisRun。

验收标准：

- 刷新后 run 不重复执行；
- 同一 idempotency key 不产生重复 run；
- stage result 成功后立即持久化；
- 保留当前可见的渐进渲染体验。

### 7.4 热点分析 workflow

目标：基于账号概况和趋势数据识别热点机会并生成选题。

输入：

- 账号概况实例；
- 趋势数据实例；
- demo/live mode。

执行要求：

- CSV 在模型调用前确定性解析和排序；
- 保留 top-50 engagement ranking 行为；
- graph state 不存完整 CSV；
- input snapshot 只保存 compact ranking 和 source material ID。

输出：

- trend pattern analysis；
- pain point analysis；
- topic generation；
- title variants；
- AnalysisRun。

### 7.5 视频博主质量诊断 workflow

目标：帮助创作者运营判断 AIGC 视频创作者质量和激励计划适配度。

输入：

- 账号概况实例；
- 小红书创作者主页实例，后端确定性派生 video creator evidence pack；
- 或兼容路径：视频创作样本实例；
- 可选图文/视频素材实例，用于提供已保存的 compact media understanding。

注意：

- XHS evidence pack 应包含 video note 数量、高互动内容、评论反馈、封面媒体引用、商业/剧本/技术探索信号和证据限制；
- 如果没有已确认的 video understanding，模型不得声称看过完整视频、镜头、剪辑、口型或音频；
- 文本化视频创作样本仍作为兼容输入；
- 如果用户先保存 Qwen 图片/视频理解结果，workflow 可以读取 compact media understanding；
- workflow graph state 只保存输入资产 ID、媒体资产 ID 和阶段结果，不保存完整 XHS JSON、完整媒体文件或完整 derived JSON；
- 本地上传视频可通过 ffmpeg 抽取预览帧，再由 Qwen 图片/视频理解 skill 生成结构化理解草稿；
- 当前不做真实视频链接抓取、平台数据抓取或完整本地视频直传；
- 因此诊断必须显式受 evidence pack 的证据限制约束，并在每个 stage result 中持久化 evidenceScope、evidenceConfidence、evidenceLimitations 和 recommendedNextEvidence；
- video quality stage 还必须持久化 cannotAssess，用于说明因为缺少视频/图片理解而不能可靠判断的维度。

输出：

- creator profile；
- video quality diagnosis；
- incentive fit judgement。

产品判断示例：

- 剧本驱动型：通常更适合激励计划；
- 商单驱动型：激励计划较难改变其行为；
- 技术探索驱动型：需要结合内容稳定性、受众反馈和创作动机分类讨论。

补充规则：右侧 workflow 调用区的“下期选题”不是账号诊断、热点分析或视频质量诊断的必填项。它只作为受众模拟的测试内容：用户可以手动输入，也可以从选题卡或选题库填入；demo 模式只在用户实际发起受众模拟时自动补样例。

### 7.6 选题库流程

目标：把 workflow 生成的候选选题沉淀为可复用 Topic。

流程：

1. 用户在分析结果中看到 topic cards。
2. 用户保存到选题库。
3. 用户可设为当前选题。
4. 用户可编辑 title 和 angle。
5. 用户可 archive。
6. 用户可调用 Brief 生成、结构生成或发送到受众模拟。

验收标准：

- topic 记录应保留 source workflow 和 source analysis run；
- 手动创建 topic 也应进入同一 Topic 模型；
- 当前选题可以被后续 workflow 引用。

### 7.7 创作输出流程

目标：从选题生成可执行的创作 Brief，再从 Brief 或 Topic 生成可继续编辑的内容结构。

流程：

1. 用户选择 Topic。
2. 用户点击生成创作 Brief。
3. 后端生成 `Draft(kind=content_brief)`。
4. 用户检查或编辑 Brief。
5. 用户从 Brief 继续生成内容结构。
6. 后端生成 `Draft(kind=content_structure)`，并在 input snapshot 中记录 sourceBrief。
7. generated snapshot 持久化。
8. 用户编辑内容时写入 editable content。

兼容行为：

- 用户仍可从 Topic 直接生成内容结构；
- 但推荐链路是 Topic → Content Brief → Content Structure。

验收标准：

- 不再存在 production fake structure；
- 每个生成结果必须有 Draft record；
- 用户编辑不覆盖 generated snapshot；
- Brief 和 Structure 通过 Draft.kind 区分；
- 从 Brief 生成结构时，结构生成应使用 Brief 的 editable content，而不是只使用 Topic 标题。

### 7.8 受众模拟 workflow

目标：对选题或草稿进行多 persona 反应模拟。

输入：

- saved Topic；
- 或手动输入 topic；
- 可选 Draft。

执行：

1. derive personas；
2. parallel initial reactions；
3. parallel debate responses；
4. synthesis；
5. finalize。

输出：

- persona definitions；
- initial reactions；
- debate responses；
- synthesis；
- SimulationRun。

验收标准：

- 单个 persona 失败不应导致全部结果丢失；
- previous simulation 可以重新打开；
- simulation history 出现在 workspace 内。

### 7.9 Agent conversation / Capability Maker

目标：通过对话生成 Skill / Agent / Workflow 或资产修改 proposal。

流程：

1. 用户进入 Skills / Agents / Workflows。
2. 用户点击 Capability Maker。
3. 对话自动携带 workspace broad context 和当前选中的 capability asset detail。
4. agent 返回解释和 proposed actions。
5. proposed actions 持久化为 AssetProposal。
6. 用户可以编辑 pending proposal。
7. 用户 apply 或 reject。

验收标准：

- Maker 必须看到 capability catalog；
- 如果用户从具体资产进入，必须带上当前资产 detail；
- capability proposal 必须给出可应用的完整 definition；
- apply 支持创建新能力资产和更新已有能力资产；
- 引用不存在的 skill / agent 时必须失败并持久化错误；
- apply/reject 状态必须持久化；
- 不应直接静默修改资产。

## 8. 非目标：批量能力

批量导入和批量 workflow 暂时不是产品目标。当前判断是：批量会显著增加输入校验、进度展示、错误恢复、结果对齐和测试维护成本，但现阶段真正需要验证的是单个创作者档案、单次 workflow 和 agent-assisted 资产整理是否足够顺滑。

当前产品应优先支持：

- 单个输入资产实例的新建、编辑、保存和另存为；
- 单个小红书创作者主页离线导入包上传；
- 单次 workflow 对当前选择资产运行；
- 历史结果重新打开和复盘；
- agent 帮用户整理输入资产草稿。

后端遗留 batch endpoint 可以暂时保留为兼容路径，但不在前端暴露，不进入近期路线，也不新增验收要求。

## 9. 模型调用要求

### 9.1 Provider

当前支持：

- Qwen OpenAI-compatible path（默认）；
- Anthropic-compatible path（显式兼容配置）。

自动化测试默认使用 fake provider。

配置边界：

- 文本模型默认通过 `MODEL_PROVIDER=qwen` + `QWEN_*` 接入 OpenAI-compatible endpoint；
- 文本模型也可以通过 `MODEL_PROVIDER=anthropic` + `ANTHROPIC_*` 接入 Qwen 的 Anthropic-compatible endpoint；
- 图文/视频理解与生成属于 Qwen / DashScope media skills，不读取 `ANTHROPIC_*`，必须配置 `QWEN_API_KEY` 或 `DASHSCOPE_API_KEY`；
- 如果同一把 key 同时用于文本和 media，也需要在本地 env 中同时写入 `ANTHROPIC_API_KEY` 和 `QWEN_API_KEY`，或显式配置对应 alias；
- `QWEN_BASE_URL` 用于 OpenAI-compatible chat completions；`QWEN_DASHSCOPE_BASE_URL` 用于 DashScope async media task。

### 9.2 结构化输出

要求：

- 尽量使用 JSON response format；
- 支持 fenced JSON；
- 支持响应前后带说明文字时提取 JSON object；
- 支持 `data/result/output` 外层包裹解包；
- 支持常见 root 字段别名归一，例如 `pain_points -> painPoints`、`proposed_actions -> proposedActions`、`video_quality -> videoQuality`；
- 支持 OpenAI-compatible `function_call/tool_calls.arguments` 作为结构化输出来源；
- 对缺字段做 validation；
- 失败时生成 stage error 或 assistant failure message。

当前结构化输出校验是 operation-level root schema，不是完整 JSON Schema。它能防止最常见的错根字段和错容器类型，但还不能保证每个 nested field 都完整正确。下一步如果真实响应出现更多边缘形态，应优先补脱敏 fixture，再决定是否引入字段级 repair。

### 9.3 Smoke test 要求

当前必须保留以下 smoke test：

- `scripts/smoke_model_api.py --operation pain_points`：验证文本结构化模型调用；
- `scripts/smoke_model_api.py --operation agent_chat`：验证 agent conversation 的 live schema；
- `scripts/smoke_qwen_media.py image-understand`：验证 media skill 的 Qwen vision path。
- `scripts/smoke_live_workflows.py --mode demo --workflow all`：不打开前端，走真实 FastAPI 路径验证账号诊断、热点分析、视频博主质量诊断三条 workflow；加 `--mode live` 才会调用真实文本模型。

最近一次真实 smoke 结果：

- `pain_points` 通过；
- `agent_chat` 通过；
- `image-understand` 通过；
- 当前本地 `backend/.env.local` 已补齐文本模型和 media skills 所需变量，且被 git ignore。

这些 smoke test 不进入常规自动化测试，因为会消耗真实模型额度，也依赖网络环境。

### 9.4 Context 控制

虽然 Context Access Layer 倾向 broad context，但 workflow node 仍应避免把完整 workspace 无脑传给每个模型调用。

要求：

- workflow node 只接收该 stage 必要上下文；
- maker/conversation 可以接收 broad workspace context；
- 每次 context pack 应可审计；
- full source material 不放入 graph state，只通过 ID 和 snapshot 连接。

## 10. 数据持久化要求

SQLite 保存：

- workspace；
- input asset metadata/text；
- analysis runs；
- stage results/errors；
- topics；
- drafts；
- simulation runs；
- skills；
- agents；
- workflows；
- conversations/messages；
- content collaboration sessions/messages/runs；
- asset proposals；
- graph checkpoints；
- idempotency keys / execution mapping。

磁盘保存：

- uploaded trend CSV 文件。

不保存：

- 客户端传入的任意文件系统路径；
- 模型 API key 到前端；
- 任意用户上传文件树；
- 通用代码执行结果。

## 11. API 产品要求

API 应保持产品语义，不暴露 LangGraph 内部术语。

前端不应看到：

- graph node；
- thread；
- checkpoint；
- LangGraph run。

前端应看到：

- AnalysisRun；
- SimulationRun；
- ActivityEvent；
- stage result；
- status；
- asset；
- proposal。
- collaboration session、角色消息和面向创作者的协作状态（后续画布入口）；

当前 API 请求使用相对路径 `/api/...`，便于后续 VPS 反代。

## 12. Demo / Live 模式

### Demo 模式

要求：

- 提供接近原始 HTML 原型的默认样例；
- 不依赖真实模型；
- 适合快速演示完整链路；
- 不应出现 production fake 资产污染真实路径。

### Live 模式

要求：

- 通过后端 provider 调用模型；
- API key 只存在后端环境；
- 失败有明确错误状态；
- conversation / workflow 结果持久化。

## 13. 非目标

当前明确不做：

- 用户账号系统；
- 多租户和组织管理；
- 权限系统；
- sharing/collaboration；
- cloud object storage；
- arbitrary file editing；
- generic file tree；
- vector database；
- plugin marketplace；
- MCP；
- VS Code clone；
- 用户侧 workflow nodegraph editor；
- 任意代码工具调用。

## 14. 当前已知限制

1. 视频博主质量诊断优先使用小红书创作者主页派生的 compact evidence pack，兼容文本样本；可读取已保存的 compact media understanding，但不自动抓取或解析视频链接。
2. 图文/视频素材已经接入 Qwen 理解、生成和本地视频预览抽帧；仍没有独立 OCR、ASR、平台抓取或长视频语义切片。
3. Skills 是受控产品能力，不是任意代码工具；formatter skills 与 media skills 可直接 invoke，分析/选题/草稿/模拟/视频诊断类 skills 可 dry-run。
4. Workflow assets 不是可视化 nodegraph editor。
5. Conversation 后端执行已有 SQLite job 记录和启动恢复，但仍是单进程本地 worker，不是带跨进程 claim/lease 的完整 durable queue。
6. SSE 是 observation replay，不是完整 durable event log。
7. AssetProposal 已支持 pending 状态下编辑后 apply，并对 skill / agent / workflow proposal 做基础字段和引用校验；apply 前已有后端 diff preview，但前端仍主要是 JSON editor，不是表单化编辑器。
8. qwen 结构化输出已有 operation-level 根字段校验、常见别名归一和脱敏 fixture 测试；仍可继续补字段级 repair。
9. 批量能力已从当前产品目标移除；后端遗留 batch endpoint 暂时只作为兼容路径。
10. 如果本地只配置 `ANTHROPIC_*`，文本模型 live 可用，但 Qwen media skills 不可用；media skills 需要单独的 `QWEN_*` / `DASHSCOPE_*` 配置。

## 15. 成功指标

当前阶段建议用内部产品指标，而不是商业指标。

### 15.1 资产沉淀指标

- 每次 workflow 运行前必要输入均有持久资产；
- 每次生成结果均有 AnalysisRun / Topic / Draft / SimulationRun 记录；
- 刷新后可以恢复历史结果。

### 15.2 workflow 稳定性指标

- 重复提交不产生重复 run；
- 中断连接不影响后端执行；
- stage failure 可被持久化和重新查看；
- fake provider 自动化测试稳定通过。

### 15.3 可维护性指标

- App.tsx 持续拆分；
- 新增 workflow 时复用产品资产模型；
- 新增 skill/agent/workflow 时进入能力资产 catalog；
- 上下文输入有可审计 context pack。

# 创作者内容诊断与选题共创助手 · 面试讲解稿

> 配合 `index.html`(双击打开)。下面按面试节奏组织:一句话定位 → 现场演示动线 → 设计取舍 → 技术实现 → 局限与下一步。挑能讲的讲,不用全背。

---

## 0. 一句话定位(开场)

> 「这是一个帮内容创作者做**选题决策**的 Agent 原型，有两条并行工作流：一条是**账号自比诊断**，把创作者自己的历史数据拿来"爆款 vs 扑街"做对比，找出账号独有的爆款公式；另一条是**全域热点分析**，把某话题下的全平台热帖 CSV 批量导入，分析行业内容规律，找到当前的内容机会窗口。两条流的诊断结果都可以一键触发**多智能体受众模拟**——让不同类型的读者 agent 辩论这篇内容，把发布后才知道的反馈拉到发布前。」

钩子:这不是一个"AI 写作工具",而是一套**从个人账号 + 行业数据双轨驱动选题的诊断引擎**。

---

## 1. 现场演示动线(2 分钟,照着点)

**路线 A · 账号自比诊断（用你自己的数据）**

1. 打开页面,点 **「↺ 载入样例」** → 载入真实账号 **@QSheep(留学赛道,1.4K 粉)** 的定位 + 历史笔记 + 真实评论。
2. 点 **「⚡ 生成诊断」** → 右侧四段依次出现:
   - **① 主页诊断**:对 3 篇爆 / 2 篇平差做对比 → 反推爆款变量和可执行结论,归纳标题公式和爆款结构模板
   - **② 痛点归类**:评论区聚成高频痛点主题,带强度、条数、原文证据
   - **③ 选题生成**:每条选题带「为什么适合这个账号」,结合①的爆款基因做匹配
   - **④ 结构复盘**:最优选题的逐段骨架 + 可跨选题复用的表达结构
3. 点 ③ 某条下面的 **「→ 填入下期选题」** → 切到受众模拟（见下）

**路线 B · 全域热点分析（用行业热帖数据）**

1. 点左上角 **「🔥 热点分析」** tab → 载入样例 → 数字游民话题 50 条热帖 CSV 自动填入
2. 填入话题关键词（「数字游民」），点 **「⚡ 热点分析」** → 四段结果:
   - **① 热点归纳**:识别高频主题、爆款规律、当前内容机会窗口（「需求强但供给少」的角度）
   - **② 痛点归类**:从热帖标题和内容推断读者高频痛点
   - **③ 选题生成**:每条带「为什么现在热 + 为什么适合这个账号」双重约束
   - **④ 结构复盘**:为最优选题写逐段骨架

**共用 · 受众模拟**

3. 任意一条流里点「→ 填入下期选题」→ 点 **「👥 受众模拟」**:
   - 3 类受众原型并行读内容,各自初读反应先后亮起
   - 看到彼此的反应后互相辩论（认同/反驳/补充）
   - 综合评估：最有共鸣受众、潜在争议点、优化建议

4. 切到 **「实时生成 · Claude API」** 模式(现场有网+key):同样输入实时调模型 → 证明演示模式是同一套逻辑的预存结果,不是写死的假数据

**一句收尾**:两条流解决不同维度的选题盲区——A 回答「我靠什么赢」,B 回答「市场现在在赢什么」,受众模拟在发布前做一次压力测试。三者组合是一个闭环。

## 2. 关键设计取舍(面试官最爱问"为什么这么做")

**Q:数据从哪来?小红书没有公开 API。**
> 这是整个项目最现实的瓶颈,我没回避。第三方爬虫有合规和稳定性风险,所以原型阶段我选**手动/半自动喂数据**——创作者把对标笔记和评论粘进来。这样:① 立刻能跑、完全合规;② 先验证"分析质量值不值",采集是第二阶段的工程问题,不该卡住价值验证。我把"采集"设计成可插拔的输入层,后面接什么数据源都不影响下游。

**Q:为什么强调"为什么适合这个账号"?**
> 选题工具最容易产出"正确的废话"。差异化在于**条件生成**——把账号定位和历史爆款特征作为约束,让选题既命中痛点、又贴合人设、还不重复。这正是我在小红书蒲公英做创作者运营时那套「平台定位-内容场景-博主匹配-转化路径」框架的延续。

**Q:演示模式是不是写死的?**
> 是预置的,但**和实时 API 走同一套 JSON schema、同一个渲染器**。这是有意的工程设计:逻辑只实现一遍,演示只是把结果缓存下来保证现场不翻车。两个模式一对比,正好说明系统的真实性。

**Q:受众模拟这个功能解决什么问题?**
> 创作者发文前最大的盲区是:这篇内容对不同读者会有什么反应,评论区会不会出现意料外的争议。传统方式只能发出去再看数据。受众模拟把这个"发布后才知道"的反馈**提前拉到发布前**——三类读者 agent 各自带着不同的背景和关切读同一篇内容,再互相辩论,让内容在多个视角下做一次压力测试。它不是模拟创作者,而是模拟读者。

**Q:为什么用 Tool Use 而不是在 prompt 里写 schema?**
> Prompt 里写"请输出 JSON"是软约束——模型会尽力,但可能在字符串里夹换行、夹引号,JSON.parse 就挂了。打补丁修坏掉的 JSON 是无底洞。Tool Use 是 API 层面的硬约束:你定义 input_schema,模型的 tool input 必须满足这个 schema,否则 API 拒绝,返回的 `content[0].input` 必然合法。这是工程上应该做的事,而不是靠 prompt engineering 来保证结构化输出。

**Q:两条工作流的数据来源不同，怎么保证选题质量是个性化的而不是通用的？**
> 两条流都有一个共同约束：账号定位。热点分析产出的选题，必须同时满足「话题热度高」AND「与账号定位匹配」，这两个条件缺一不可。路线 A 靠的是「你自己的爆款基因」作为约束，路线 B 靠的是「账号定位 + 行业热点趋势」双重约束。两条流的选题都带明确的"为什么适合这个账号"，这是防止产出通用废话的命门，也是和市面上通用选题工具的核心差别。

## 3. 技术实现(被追问时讲)

- **形态**:单文件 `index.html`,零依赖、零后端,双击即开——降低演示门槛。
- **双流架构**:两条工作流（账号诊断 A / 热点分析 B）共用同一组渲染组件，选题卡片、痛点卡片、结构骨架不重复实现；前端 tab 切换，状态隔离（generation ID 防止 Promise 回调污染）。
- **核心抽象**:统一 JSON schema（painPoints / topics / structure），**输入层、模型层、渲染层解耦**。演示模式与实时 API 共用同一渲染器，逻辑只写一遍。
- **分块请求**:四段诊断拆成3个独立 call，Phase 1 并行（Profile+PainPoints），Phase 2/3 串行，逐段渐进渲染，用户不用等全部完成才看到结果。
- **Tool Use**:痛点归类和受众模拟全程使用 Tool Use（Function Calling），input_schema 在 API 层面强制 JSON 合法，彻底解决 prompt 约束下的 JSON parse 问题。
- **CSV 解析**:前端 JS 解析，无需后端；字段名中英文映射，自动按互动量排序取 top 50 送入模型。

> 简历里提到我用 **skill + coze** 做类似的事——这个 HTML 版是为了面试能现场跑、讲清逻辑;同一套工作流我也能在 coze 上编排成多节点 bot。

## 4. 局限与下一步(主动说,显得清醒)

- **现状局限**:数据靠手动输入/CSV 上传，无自动采集；痛点归类的"条数/强度"在样本小时仅供参考；热点分析 CSV 中缺少真实评论字段（目前从标题/内容片段推断痛点）；受众模拟是单轮辩论，未实现多轮信息不对称的深度对话。
- **下一步**:
  1. 半自动采集(创作者授权下的对标笔记批量导入);
  2. 接入笔记真实表现数据(完播/互动),让"结构复盘"从经验启发升级为**数据驱动的迭代**;
  3. 选题去重记忆,跨周追踪一个账号已写过什么、热点的新鲜度;
  4. 受众原型库沉淀:每次受众模拟的结果做结构化存档,形成可横向对比的读者画像库(B 端潜力)。

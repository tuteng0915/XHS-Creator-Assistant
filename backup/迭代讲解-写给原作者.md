# 我们改了什么、加了什么、为什么这么做
 
> 目标：读完之后，你对自己项目的现在这个版本了如指掌，能完整地跟别人解释每一个功能是怎么做到的、当时为什么要这么做。  

---

## 整体变化

你交给我的时候，项目是这个状态：

- 一条工作流（账号诊断五段：主页诊断 → 痛点归类 → 选题生成 → **标题变体** → 结构复盘）
- 只有演示模式，结果是写死在代码里的，换一个输入不会有新的输出
- 多智能体受众模拟是你在 PRD 里写的"设想"，还没实现

当前版本：

- **两条工作流**：账号诊断（A 流）+ 热点分析（B 流），UI 上是两个 Tab
- **真实 Claude API 接入**：演示模式保留，新增"实时生成"模式，可以真正跑起来
- **受众模拟从【设想】变成了【已做】**：3 类读者 agent 并行评价、辩论、综合反馈
- **一堆稳定性修复**，让它在各种情况下不崩

下面逐项讲。

---

## 第一件事：让 demo 真正"活"起来

### 之前是什么样

你之前的 demo 是这样工作的：页面上有一个"生成诊断"按钮，点了之后，预设好的结果就一段段"渐进显示"出来——看起来像在生成，其实是把写好的答案一行行展示给你看。数据是真实的，但"生成过程"是表演的。

这个设计本身没有问题，面试时用真实数据讲故事是对的。但有个隐患：面试官如果问了，那会被一眼识破有点假。

### 现在怎么做

新增了"实时生成"模式（页面上那个切换按钮）。

切换到实时模式后：

1. 你每次粘贴 Claude 的 API，或者把 Claude 的 API key 放在项目同目录下一个叫 `key` 的文件里（程序启动时自动读取）
2. 点"生成诊断"，程序会自己真的去调用 Claude，实时产出结果
3. 四段结果依次出现，因为是分批请求的（第 ① 段出来了你就能看，② 还在生成中）

### 为什么这样设计

有几个考虑：

**演示模式保留**的原因：演示的稳定性和实时生成的真实性，对不同场合有不同价值。演示模式保证你在没网、没 key 的环境下也能跑；实时模式证明这不是写死的假数据。两个模式共用同一套渲染逻辑——也就是说，演示的结果就是真实 API 跑出来的结果存下来的，不是拍脑袋捏造的。

**自动读取 key 文件**的原因：API key 是很长的一串字符，每次手动粘贴容易出错，也不安全（会留在剪贴板里）。放在本地文件里、程序自动读，是更合理的习惯。

## 第二件事：受众模拟

### 你原来设想的是什么

你在 PRD §13 里写："让一个 agent 揣着隐藏的真实卡点，另一个 agent 在看不到答案的情况下去诊断"——这个模式是**让 agent 模拟创作者的用户（学员/买家）**，做盲测评估。

### 我们实际实现的是什么

我们实现了一个更贴近"内容发布"场景的变体：**不是仅仅是模拟一个用户来评估创作者，而是模拟不同类型的读者来评价一篇内容**。


**为什么这个方向更有价值**：

你写一篇留学选校的笔记，你以为所有人都会认可这个视角——但实际上：
- 正在备考的同学会很有共鸣
- 已经出国的同学可能会觉得"说的不全对"
- 家长视角的读者可能关心的是完全不同的点

这个信息本来只有发布之后、评论区炸出来你才知道。受众模拟把它**拉到发布前**。

### 具体流程是什么

分四步，每步都有模型调用：

**第一步：归纳读者原型**

程序从你的评论区（A 流）或话题关键词（B 流）里，让 Claude 归纳出 3 类典型读者。每类读者有一张"人设卡"：
- 是什么类型的人（比如"正在备考的双非焦虑生"）
- 性格特征（比如"渴望被确认、对成功案例敏感但对失败信息有防御心"）
- 最关注什么（比如"成功率、背景限制、时间成本"）

**第二步：三类读者并行初读**

三类读者同时、独立去读你填进去的下期选题（标题+切入角度）。每人给出：
- 初读感受（第一反应是什么）
- 会不会继续看下去（和理由）
- 最关心的点

"并行"意思是这三个调用是同时发出去的，不是一个等一个，速度更快。

**第三步：看到彼此反应后辩论**

三类读者看到彼此的初读反应后，互相回应。可能是认同、反驳、补充。这一步会暴露"争议点"——比如 A 类觉得这个角度很好，B 类却觉得这个说法有问题，就会在这里吵起来。

**第四步：综合评估**

由一个"第三方"的模型，基于三类读者的所有反应，给出：
- 最有共鸣的受众是哪类、为什么
- 潜在争议点（哪个角度可能引发反感或误解）
- 具体优化建议（选题角度或切入方式的调整方向）

### 和三段诊断的联动

③ 选题生成里，每条选题卡片下面都有一个 **「→ 填入下期选题」** 的按钮。点一下，这条选题的标题和切入角度会自动填进受众模拟的输入框。

这样的操作路径是：诊断出选题 → 一键填入 → 受众模拟验证 → 看看不同读者的反应。"选题"和"验证"形成了一个闭环。

## 第三件事：加了热点分析的工作流

### 为什么要加

原来的账号诊断解决的问题是：**我靠什么赢**——基于你自己的历史数据，找出你这个号独有的爆款公式。

但这有个盲区：你的爆款公式再好，如果这个方向的内容市场已经过饱和、或者热点刚好在涌现，你光看自己的数据是感知不到的。

热点分析补的就是这个盲区：**市场现在在赢什么**——把某话题下的全平台热帖批量导入，AI 来分析行业内容规律，告诉你当前的内容机会在哪里。

### 数据怎么进来

你把某话题的热帖数据导出成 CSV 文件（第三方数据平台一般都支持导出），上传进来。程序会：
1. 自动识别字段（标题、点赞、收藏等，中英文字段名都认）
2. 按互动量（赞+藏）排序，取 top 50 条
3. 把这 50 条送进模型分析

不需要后端服务器，这些处理都在你的浏览器里完成。

### B 流的四段是什么

| 段 | 干什么 |
|---|---|
| ① 热点归纳 | 识别高频主题、爆款内容形态；找出"需求强但供给少"的内容机会窗口 |
| ② 痛点归类 | 从热帖标题和内容推断读者高频痛点（不是从评论，因为导出数据里评论字段通常不全） |
| ③ 选题生成 | 每条带双重约束："为什么现在做"（热点时效性）+ "为什么适合这个账号"（个性化匹配） |
| ④ 结构复盘 | 为最优选题写逐段骨架 |

### 和 账号诊断 流的共同约束

两条流有一个关键的共用设计：左侧的 **"账号定位"输入框是共用的**。

这个设计的逻辑是：热点分析出来的选题，也必须过"这和我的账号定位匹配吗"这道筛子。不然热什么写什么，就变成了追热点、没有账号人设，选题和"为什么是你来写"就断开了。

共用这个输入框，让 热点分析 流的每条选题都自带个性化约束，防止产出通用废话。

### 热点分析 流的演示样例

热点分析 流的预制样例用的是"数字游民"这个话题，数据来自真实热帖 CSV（50 条）。受众模拟的预制样本也是配套的：3 类读者原型分别是"想转型但还没迈出去的传统职场人"、"已实现远程工作的数字游民"、"理性评估风险的稳健型"。

## 第四件事：稳定性——为什么之前会报错，现在怎么解决的

这部分不需要你懂技术细节，但需要理解"是什么问题、怎么想到这个解法"，这样面试时被追问"遇到什么技术挑战"你能说得出来。

### 问题一：AI 输出格式不稳定，页面报错崩溃

**是什么问题**

程序拿到 AI 的回答后，需要把它解析成结构化的数据（JSON 格式），才能渲染成漂亮的卡片。

但 AI 的输出是文本，它有时会在文字里夹杂换行符、或者引号没对齐，程序一解析就崩。你之前遇到的"JSON parse error"就是这个。

**怎么解决**

换了一种叫 **Tool Use（Function Calling）** 的 API 使用方式。

打个比方：原来的方式是让 AI"写一份 JSON 格式的报告"——它会尽力，但格式不保证。

Tool Use 的方式是让 AI "填一张规定好格式的表格"——哪些字段必填、填什么类型，都在 API 层面写死了。AI 的回答如果不符合表格格式，API 直接拒绝，不会给你一个坏的结果。

这叫"硬约束"，比 prompt 里写"请输出 JSON"的"软约束"可靠得多。

受众模拟全程（归纳读者原型 → 初读反应 → 辩论 → 综合评估）都用 Tool Use，所以那一块一直很稳。

### 问题二：切换工作流时，旧的请求"追回来"污染界面

**是什么问题**

假设你在 A 流（账号诊断）点了"生成"，AI 开始工作，需要 20 秒。你等不及，切到 B 流（热点分析）。

15 秒后，A 流的结果回来了。程序不知道你已经切到 B 流了，就把 A 流的结果写进了 B 流的界面——内容全乱了。

**怎么解决**

每次发起新请求，程序生成一个"本次请求 ID"（自增的数字）。等结果回来的时候，先检查"这个结果的 ID，还是当前界面的 ID 吗"——不是的话，直接丢弃，不渲染。

打比方：外卖的订单号系统。旧订单送到了，发现单号对不上，就不签收。

### 问题三：等待时间太长，界面一直空白

**是什么问题**

最开始的版本，四段诊断是一个请求里全部做完的——等待时间可能 30-40 秒，期间界面完全空白，用户不知道在发生什么。

**怎么解决**

拆成多个独立请求，分批发出去：
- 第 ① 段（主页诊断）和 ② 段（痛点归类）**同时发出**，谁先回来谁先显示
- 等这两段都回来了，再发 ③ 段（选题生成）
- 等 ③ 回来，再发 ④ 段（结构复盘）

这样的效果是：大约 5-8 秒后，第一段结果出来了，你可以先看着；之后每隔几秒，下一段结果出来；整体等待时间缩短，也不再是"空白等待"。

## 第六件事：文档同步更新

### PRD 改动

主要改动：
- **§5 功能范围**：从单流五段，改成 5.1（A 流四段）和 5.2（B 流四段）两节，附 CSV 字段规范

- **§8 迭代路线**：MVP 描述更新为"两条流均已跑通"
- **§13 多智能体**：加了一段"已实现的变体"，描述我们实际做的和原设想的区别，以及为什么

### 面试讲解稿更新

主要改动：
- 一句话定位升级：从"五段工作流 AI 诊断 Agent"改为"双轨驱动选题的诊断引擎"
- 演示动线拆成三段：路线 A + 路线 B + 共用受众模拟，对应两条流的演示节奏
- 替换了一个 Q&A："为什么用 Haiku+Sonnet 混搭"（现在不混搭了，全用 Sonnet）→ "两条工作流如何保证个性化"（更有产品价值的问题）
- 技术部分更新了双流架构要点（CSV、Tool Use、generation ID 都加进去了）
